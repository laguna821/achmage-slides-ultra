# R-004 — 플러그인 로딩 성능·경량화 및 번들 구성 최적화

## Executive summary

- **현재 상태:** 조사 범위만 등록한 `draft`다. 성능 baseline을 아직 계측하지 않았으므로 계획에서 근거로 사용할 수 없다.
- **분리 결론:** R-003의 Scorecard 목표는 static warning, capability, release scan 및 file-size threshold를 다룬다. R-004는 실제 cold/warm plugin load, first preview, first stable render, CPU·memory를 다룬다. 성공 지표가 다르므로 별도 R-ID가 맞다.
- **연계 방식:** R-003에서 얻은 bundle composition과 build 후보는 R-004의 가설 입력으로만 사용한다. bytes 감소를 latency 감소로 간주하지 않는다. 이후 하나의 구현 계획이 필요하면 complete 상태의 R-002, R-003, R-004를 함께 인용할 수 있다.
- **남은 불확실성:** Obsidian/Electron version, OS cache, vault 규모, font cache, 첫 view 여부, math engine, document 크기가 측정값을 크게 바꿀 수 있다. 고정 harness와 scenario가 먼저 필요하다.

## Research brief

### 배경과 의사결정

현재 `main.js`는 크고 MathJax, Highlight.js, embedded fonts/backgrounds가 주요 비중을 차지한다. 그러나 bundle byte 비중은 모듈 초기화 시간, JavaScript parse/eval 시간, first Open Slide Preview, Pretext measurement, Marp render 또는 memory cost와 동일하지 않다. 이 조사는 다음 제품 결정을 가능하게 해야 한다.

1. 실제 사용자가 느끼는 병목은 plugin enable, view open, parse, render, asset decode 중 어디인가?
2. 아키텍처를 유지한 최적화로 유의미한 개선이 가능한가?
3. eager/lazy initialization, dependency import surface, syntax highlighter, math engine, embedded asset 중 무엇을 건드릴 가치가 있는가?
4. Scorecard size 개선 후보가 실제 성능에도 이득인지, 아니면 별개인지?
5. 어느 latency/memory budget을 release regression gate로 삼을 것인가?

### 핵심 질문

1. Obsidian 시작 시 plugin `onload()`의 cold/warm median과 p95는 얼마인가?
2. 명령 실행부터 Open Slide Preview shell이 보일 때, 첫 slide가 보일 때, font/layout이 안정될 때까지 각각 얼마인가?
3. 작은 문서, 긴 2D 문서, math-heavy, code-heavy, image-heavy document에서 병목이 어떻게 달라지는가?
4. MathJax, KaTeX, Highlight.js, Marp/PostCSS, Pretext, embedded assets의 parse/eval/init/render 비용은 각각 얼마인가?
5. view를 열기 전에도 초기화되는 dependency나 asset가 있는가?
6. lazy import 또는 on-demand engine init이 first useful paint를 개선하면서 최초 사용 지연만 옮기지는 않는가?
7. browser-platform build 또는 dependency patch가 실제 Electron runtime load와 memory를 개선하는가?
8. background/font payload가 module parse, base64 decode, font registration, memory에 미치는 영향은 무엇인가?
9. plugin disable/re-enable, hot reload, second preview의 warm behavior는 어떤가?
10. optimization이 deterministic overflow, exported HTML, math/code language 호환성을 바꾸지 않는가?

### 반증 질문

1. `main.js`를 크게 줄여도 first preview가 거의 빨라지지 않는가?
2. lazy loading이 plugin startup은 줄이지만 첫 presentation을 더 느리게 만드는가?
3. 평균은 개선되지만 p95 또는 large-document latency가 악화되는가?
4. dependency trimming이 rare syntax/math/theme/asset 기능을 퇴행시키는가?
5. 측정값이 OS file cache, DevTools, hot reload 또는 font cache 효과일 뿐인가?
6. instrumentation 자체가 timing과 memory를 왜곡하는가?

### 성공 기준

- versioned benchmark harness, fixtures, raw result artifact와 재현 명령이 저장소에 남는다.
- hardware, OS, Obsidian/Electron, Node, plugin commit, vault/fixture, cache 상태가 기록된다.
- 최소 cold/warm, first/second preview, small/large/math/code/image scenario를 분리한다.
- 각 scenario를 충분히 반복하고 median, p95, dispersion 및 실패/outlier 처리 규칙을 기록한다.
- plugin load, shell ready, engine ready, first DOM, font/layout stable, audit complete milestone을 구분한다.
- bundle metafile과 runtime trace를 연결하되 상관을 인과로 단정하지 않는다.
- 후보별 expected benefit, measured benefit, compatibility cost, rollback 조건을 제공한다.
- 성능 budget과 regression threshold가 실제 baseline/variance로 정당화된다.
- R-002 navigation, R-003 Scorecard 및 deterministic overflow acceptance를 보존한다.
- 위 조건 전에는 `complete`로 전환하지 않고 어떤 P-ID도 이 보고서를 plan gate 근거로 사용하지 않는다.

## Baseline and method

- **기준 커밋:** `b061ce8c4aa528cb6b909f64a87a78a342b2f1d9`.
- **현재 알려진 정적 기준:** R-003에 committed `main.js` 5,254,896 bytes와 provisional bundle composition/target 실험이 기록돼 있다.
- **아직 없는 기준:** plugin load/preview latency, CPU profile, heap/memory, first stable render marker는 계측하지 않았다.
- **제안 환경 기록:** Windows version, CPU, RAM, storage, power mode, Obsidian/Electron version, active plugins, theme, vault size, display scale.
- **제안 cache 조건:** app/process 완전 종료 후 cold, 동일 process의 second open을 warm으로 분리한다. OS disk cache를 완전히 통제할 수 없으면 그 한계를 명시한다.
- **제안 instrumentation:** `performance.mark/measure`, deterministic view/render milestones, Chromium Performance trace, memory snapshots, esbuild metafile. DevTools open 유무를 고정한다.
- **제안 반복:** 사전 warm-up을 별도 표시하고 scenario별 반복 수를 pilot variance로 결정한다. 기본 후보는 최소 20회이며 최종 수는 power/variance 근거로 확정한다.
- **제안 비교:** 한 번에 한 변수만 바꾼 candidate commit을 baseline과 번갈아 실행하고 raw JSON/trace를 보존한다.
- **방법의 한계:** 실제 사용자 vault와 hardware 다양성을 한 환경이 대표하지 못한다. synthetic fixture와 한 명의 desktop profile 결과를 일반화하지 않는다.

## Current-state evidence

### R-003에서 인계된 가설

- `main.js`는 5,254,896 bytes이며 Scorecard size warning이 있다.
- provisional metafile에서는 MathJax, project source/assets, Highlight.js가 큰 byte 축이다.
- provisional browser-platform build는 약 30KB 감소하고 render fixture parity를 보였지만 live UI와 actual latency를 측정하지 않았다.
- 26-language Highlight 후보는 약 1MB 감소하지만 rare language highlighting을 잃는다.
- embedded fonts/backgrounds는 큰 source payload지만 외부화는 current packaging contract를 바꾼다.

이 항목들은 성능 Finding이 아니다. 모두 benchmark에서 반증 가능한 hypothesis로 취급한다.

## Findings

아직 없음. 이 보고서는 `draft`이며 성능 측정 전에는 F-ID를 발행하지 않는다.

## Impact analysis

### 제품과 UX

성능 개선은 first useful preview를 기준으로 평가하며, 기능 삭제로 숫자만 낮추지 않는다.

### 아키텍처와 데이터

조사 단계에서는 instrumentation과 read-only profiling만 한다. lazy import나 packaging 변경은 complete Finding과 승인 계획이 있어야 한다.

### 성능과 자원 사용

평균만 보지 않고 median, p95, memory peak와 steady state를 분리한다.

### 보안과 개인정보

benchmark fixture에는 개인 vault 데이터를 넣지 않는다. remote resource scenario는 통제된 URL 또는 local test server를 사용한다.

### 호환성과 마이그레이션

MathJax/KaTeX, syntax languages, themes, popout, export, persisted settings를 candidate마다 유지 검증한다.

### 테스트와 관측 가능성

Instrumentation marker가 production에서 제거되는지, 남긴다면 overhead budget을 정한다.

### 빌드, 배포, 문서

Raw benchmark artifact의 보존 위치와 CI에서 실행 가능한 microbenchmark/수동 Electron benchmark의 경계를 정한다.
