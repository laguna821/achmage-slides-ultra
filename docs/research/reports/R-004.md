# R-004 — 플러그인 로딩 성능·경량화 및 번들 구성 최적화

## Executive summary

- **2026-08-05 1.2.0 owner 결정:** 최초 `b5f8ece` strict 결과와 Candidate A의 fixture-level 실패는 그대로 보존한다. 다만 실제 MP4 결과가 기능적으로 정확하다는 owner 확인 뒤, 1.2.0 release blocker는 warm/cold 각각의 **aggregate** enable·first Preview·`heapAfterFirst` 비악화로 확정했다. Candidate A `f02e20d`는 이 여섯 aggregate gate를 모두 통과하므로 유지하며 재측정하지 않는다. fixture별 p95·paired CI와 analyzer의 기존 `pass:false`는 진단으로 남고 성능 개선 claim에는 사용하지 않는다.
- **결론:** `selected-theme registration + adaptive settle` 복합 후보는 `1.1.0`에 넣지 않는다. warm plugin enable은 유의미하게 빨라졌지만 cold-process enable과 first stable preview가 사전 합의한 이중 지표 gate를 통과하지 못했다. 성능 제품 변경 없이 UX·Scorecard 릴리스를 진행하는 것이 근거에 맞다.
- **실측 범위:** 공식 `1.0.3` release `main.js`와 외부 임시 clone에서만 만든 후보를 격리 vault의 Obsidian app package 1.13.4에서 비교했다. warm은 5 fixture × 20 paired samples × 2 variants = 200건, cold-process는 small fixture × 20 pairs = 40건이며 실패는 0건이다.
- **핵심 수치:** warm enable median은 157.65→89.20ms(-43.42%, PASS)였지만 warm first preview는 356.45→315.20ms(-11.57%, 요구 threshold 18.40%, FAIL)였다. cold enable은 464.60→420.95ms(-9.40%, 요구 16.62%, paired CI가 0을 포함, FAIL), cold first preview는 475.45→474.15ms(-0.27%, FAIL)였다.
- **반증:** 후보는 583 bytes 더 컸지만 warm enable은 빨라졌다. byte size와 runtime latency를 같은 지표로 취급하면 안 된다는 R-003/R-004의 가설을 실제로 확인했다.
- **호환성:** 후보 임시 clone의 typecheck/build와 overflow matrix 36/36이 통과했고 worst overflow는 0px였다. 그러나 후보가 성능 gate에서 먼저 탈락했으므로 별도 theme/popout/export 정식 호환성 tranche는 실행하지 않았다.
- **유효기한:** Obsidian app package와 Electron이 자동 갱신되면 분산과 절대값이 바뀐다. 이 보고서의 제품 결정은 `1.1.0` 범위에는 충분하지만, 성능 최적화를 다시 추진할 때는 `review_by` 전에 환경과 baseline을 재측정한다.

## Research brief

### 배경과 의사결정

`main.js`에는 Marp/MathJax/Highlight, embedded fonts/backgrounds와 일곱 bundled theme가 들어 있다. 그러나 bundle 구성 비중만으로 plugin module load, `onload()`, first Open Slide Preview, audit settle 및 memory 비용을 판정할 수 없다. 이번 조사는 다음 한 가지 구현 결정을 닫기 위해 수행했다.

> 아키텍처와 기능을 유지하는 복합 후보가 plugin enable과 first stable preview를 **동시에**, 실제 분산보다 크게 개선하는가? 아니라면 `1.1.0`은 성능 제품 변경 없이 출시해야 하는가?

### 핵심 질문

1. app가 준비된 뒤 plugin load/evaluation과 `onload()`를 포함한 enable latency의 warm/cold-process median·p95는 얼마인가?
2. Open Slide Preview command부터 audit 완료, iframe font ready, 두 animation frame 경과까지의 first/second preview latency는 얼마인가?
3. small, long 2D, math-heavy, code-heavy, image-heavy fixture에서 결과가 일관적인가?
4. selected-theme registration과 adaptive resource/layout settle이 단지 startup 비용을 first preview로 이동하는가?
5. median 개선이 baseline MAD보다 크고 paired interval로도 방향이 확인되는가?
6. p95, memory diagnostic, long task 또는 deterministic overflow가 퇴행하는가?

### 반증 질문

- warm enable만 개선되고 cold enable 또는 first preview는 개선되지 않는가?
- 일부 fixture만 빨라지고 small/long/image 같은 일반 경로는 noise band 안에 머무는가?
- candidate p95가 median과 반대로 악화되는가?
- bundle bytes 감소가 없어도 latency가 개선되는가?
- 고정 64ms를 없애는 대신 font/image/layout 안정성을 약화시키는가?

### Candidate C-001 — benchmark-only composite

후보는 baseline tag의 외부 임시 clone에서만 만들었고 저장소 제품 파일은 수정하지 않았다.

   - audit의 무조건 64ms delay를 `fonts.ready + pending image decode`와 64ms cap의 race로 바꾼다.
   - 그 뒤 두 animation frame을 기다린 후 probe한다.
   - load-timeout과 load-event가 중복 probe를 시작하지 않도록 guard한다.

### Measurement protocol

- **Warm:** app process 하나에서 fixture별 unrecorded warm-up 2회/variant 후, variant별 20 recorded samples. plugin은 sample마다 disable/unload한다.
- **Cold-process:** sample마다 Obsidian process tree를 종료·재실행하고 app/vault ready 후 plugin을 수동 enable한다. OS page cache는 flush하지 않았다.
- 매 iteration에서 `baseline→candidate`, 다음 iteration에서 `candidate→baseline`으로 순서를 바꾼다.
- enable marker: `app.plugins.enablePlugin(id)` 호출 직전부터 promise resolve까지.
- preview marker: command 직전부터 status가 `Rendering...`을 벗어나고 iframe stage가 존재하며 iframe `fonts.ready`와 추가 2 RAF가 끝날 때까지.
- first preview 뒤 preview leaf를 detach하고 같은 plugin/fixture로 second preview를 잰다.
- 실패는 숨기지 않고 raw에 보존하도록 했으며 실제 실패는 0건이다.
- outlier를 사후 삭제하지 않았다. median/p95/MAD와 paired interval이 tail을 그대로 반영한다.

### Statistical gate

각 metric은 다음을 모두 만족해야 PASS다.

1. median improvement ≥ `max(5%, 2 × baseline relative MAD)`.
2. 10,000회 paired bootstrap의 median `baseline - candidate` 95% interval lower bound > 0.
3. candidate p95 regression이 같은 threshold를 넘지 않음.

Composite 채택은 warm/cold-process의 plugin enable과 first stable preview가 모두 통과하고 compatibility/memory regression이 없을 때만 가능하다.

- candidate `main.js`: 5,476,175 bytes, SHA-256 `a8230a02037aa4fe7fdf5af087cd6baaa6d1b92aa229c5192053a33965e665aa`

Aggregate warm enable, warm first Preview, warm heap, cold enable, cold heap은 사전 gate를 통과했다. cold first Preview median/p95는 각각 +0.70%/+0.93%로 noise band 11.89% 안이지만, paired regression 95% CI 상한 62.70ms가 absolute band 54.51ms를 8.19ms 넘어서 strict gate는 **FAIL**이다. 또한 fixture별 warm p95에서 small first Preview +28.15%(band 9.99%), long 2D enable +19.20%(10.72%), math first Preview +30.21%(6.81%), code enable +14.64%(13.55%)가 실패했다. 따라서 확정적인 일반 regression이라고 추론하기에는 분산과 표본 한계가 크지만, 사전 정의한 release gate 결과는 FAIL/inconclusive이며 AC-713을 PASS로 바꾸거나 현재 candidate를 release할 수 없다.

Read-only import/metafile 진단에서는 `src/engine/slideRenderer.ts`가 작은 draft builder 하나 때문에 `src/video/videoArtifact.ts`를 정적 import하고, 그 모듈이 다시 `src/video/videoCompositor.ts`를 정적 import해 일반 Preview/module initialization 경로에 artifact/compositor initializer가 연결됨을 확인했다. build metafile 원본 입력은 각각 93,531 bytes와 9,656 bytes이고, `videoTypes.ts`는 import 없는 3,043-byte 모듈이다. 이는 bytes만으로 latency 인과를 입증하지 않지만, MP4를 요청하지 않는 경로에서 무거운 initializer를 지연할 수 있는 좁고 기능보존형 후보를 식별한다.

2026-08-05 owner는 실제 exported MP4의 기능 정확성을 확인한 뒤, 사용자에게 체감되는 일반 load/first Preview와 memory 비악화를 **aggregate** 단위로 판단하고 fixture-level tail은 진단으로 유지하도록 release 기준을 승인했다. 이는 과거 통계 결과의 재분류가 아니라 제품 release 판단 기준의 명시적 변경이다. Candidate A는 여섯 aggregate gate를 모두 통과했으므로 유지하며, 같은 결과에서 유리한 subset을 새로 고르거나 추가 rerun을 하지 않는다. 이 근거로 loading performance가 개선됐다고 주장하지 않는다.

## Findings

### F-001 — official release asset과 canonical Git/build artifact가 일치하는 재현 가능한 1.0.3 runtime baseline이다

- **근거:** SRC-001, SRC-003.
- **내용:** GitHub asset digest와 직접 다운로드 hash가 일치했고 tag는 `b061ce8...`를 가리켰다. R-003/F-016의 tag Git blob과 격리 clean build도 같은 canonical LF bytes다. Windows checkout raw bytes만 CRLF 변환의 영향을 받으므로 실제 runtime 비교에는 직접 받은 release asset을 사용했다.
- **신뢰도:** 높음. GitHub release metadata, tag ref, 직접 계산한 SHA-256이 일치한다.
- **반례·제약:** 이후 build candidate의 content diff를 단순 EOL 차이라고 가정해서는 안 된다.
- **결정 영향:** 모든 1.0.3 runtime 비교와 candidate delta의 기준을 official release asset으로 고정한다.

### F-002 — 시작 경로에는 eager seven-theme 생성·등록이 있고 preview audit에는 고정 64ms settle이 있다

- **근거:** SRC-002.
- **내용:** `src/main.ts:29-34`는 settings load 후 renderer를 만들고, `marpEngine.ts:36-46`은 일곱 theme를 등록한다. `themeRegistry.ts:2822-2828`의 constants는 module evaluation 때 CSS를 생성하며 `auditLoop.ts:65,126`은 probe 전 기본 64ms timeout을 사용한다.
- **신뢰도:** 높음(구조). 기준 commit source에서 직접 확인했다.
- **반례·제약:** 소스 관찰만으로 해당 경로가 전체 latency의 원인이라고 단정할 수 없다.
- **결정 영향:** 두 경로를 묶은 C-001을 통제 비교하되 실측 전에는 제품 최적화로 채택하지 않는다.

### F-003 — selected-theme 복합 후보는 warm enable을 크게 개선했지만 cold-process enable gate는 통과하지 못했다

- **근거:** SRC-004, SRC-005, SRC-006.
- **내용:** warm enable은 43.42% 개선하고 paired CI가 양수였지만 cold-process enable은 9.40% 개선에 그쳐 threshold 16.62%보다 작았고 paired CI가 -1.20ms까지 내려갔다. cold p95도 639.69→722.43ms였다.
- **신뢰도:** 해당 환경에서는 높음. warm 100 pairs와 cold-process 20 pairs, 교차 순서, 실패 0건이다.
- **반례·제약:** OS page cache는 flush하지 않았고 전체 Obsidian application startup은 측정하지 않았다.
- **결정 영향:** warm disable/re-enable의 이득만으로 일반적인 plugin startup 개선을 주장하거나 C-001을 채택하지 않는다.

### F-004 — adaptive settle은 math/code warm path에는 이득이지만 first stable preview 전체 gate를 통과하지 못했다

- **근거:** SRC-004, SRC-005, SRC-006.
- **내용:** warm aggregate first preview는 11.57% 개선했지만 threshold 18.40%보다 작았다. math/code만 통과했고 small/long/image는 실패했으며 cold-process first preview는 0.27% 차이였다.
- **신뢰도:** 해당 fixture와 환경에서는 높음. 5 fixture별 20 paired samples와 cold-process 20 pairs를 사용했다.
- **반례·제약:** composite 실험이므로 adaptive settle 단독 효과와 selected-theme 단독 효과는 분리되지 않았다.
- **결정 영향:** 특정 workload 이득을 전체 first-preview 개선으로 일반화하지 않고 C-001을 기각한다.

### F-005 — 후보의 memory와 long-task tail은 채택을 뒷받침하지 않는다

- **근거:** SRC-004, SRC-005, SRC-006.
- **내용:** heap median/p95 방향이 warm/cold에서 엇갈렸고 cold long-task p95는 18.68% 늘었다.
- **신뢰도:** 낮음~중간. `performance.memory`와 renderer-wide Long Task Observer는 diagnostic이며 explicit GC, heap snapshot, call attribution이 없다.
- **반례·제약:** long-task 증가는 Obsidian renderer의 다른 작업일 수 있어 candidate 인과로 단정할 수 없다.
- **결정 영향:** 명확한 regression이라고 선언하지 않지만 candidate 안전성을 뒷받침하는 근거로도 사용하지 않는다.

### F-006 — 후보는 측정한 범위의 기능 정확성을 보존했지만 완전한 release compatibility 검증까지 가지 않았다

- **근거:** SRC-007.
- **내용:** candidate typecheck/build, live samples 240/240, overflow 36/36이 통과했고 worst overflow는 0px였다.
- **신뢰도:** 측정한 범위에서는 높음.
- **반례·제약:** overflow matrix는 `cmds-dark-native-1920-v5` 중심이며 theme/popout/export 전체 matrix는 실행하지 않았다.
- **결정 영향:** 후보가 명백히 깨졌다고 볼 수는 없지만 release compatibility 완료라고 주장하거나 채택하지 않는다.

### F-007 — C-001은 이중 지표 채택 조건을 충족하지 않으므로 1.1.0 성능 tranche는 no-change가 맞다

- **근거:** SRC-004, SRC-005, SRC-006, SRC-007.
- **내용:** warm enable 하나의 PASS로 cold enable과 first preview FAIL을 덮을 수 없으므로 C-001은 dual-metric 채택 조건을 충족하지 않는다.
- **신뢰도:** 높음. 결론은 사전 정의한 gate를 그대로 적용한 결과다.
- **반례·제약:** 후보의 두 구성요소를 단독으로 재실험하면 다른 결론이 나올 수 있으나 이번 composite 채택 결정은 바뀌지 않는다.
- **결정 영향:** candidate source·bundle·runtime marker를 제품 branch에 가져오지 않고 AC-209는 실측 no-change로 닫는다.

### F-008 — bundle bytes는 latency의 대리 지표가 아니며 runtime gate는 환경별로 다시 세워야 한다

- **근거:** SRC-003, SRC-006.
- **내용:** candidate는 583 bytes 커졌지만 warm enable은 43.42% 개선됐다. 절대 latency는 app package, Electron, OS cache, hardware와 marker에 종속된다.
- **신뢰도:** bytes/해당 환경 결과는 높음, 다른 환경 일반화는 중간 이하.
- **반례·제약:** 큰 bundle 감소가 다른 후보에서 parse/eval을 줄일 가능성까지 부정하는 결과는 아니다.
- **결정 영향:** Scorecard size warning, runtime latency, overflow correctness를 독립 gate로 유지하고 환경 변경 시 rebaseline한다.

### F-009 — exact 1.2.0 candidate는 aggregate median이 안정적이어도 사전 AC-713 tail gate를 통과하지 못했다

- **근거:** SRC-010, SRC-011.
- **내용:** warm/cold aggregate median regression은 0.15~2.01% 범위였고 대부분의 aggregate gate는 PASS였지만, cold first Preview paired CI 상한과 네 fixture의 warm p95가 허용 band를 넘었다.
- **신뢰도:** gate 판정은 높음, 지속적인 실제 regression이라는 인과 추론은 중간 이하. alternating 최소 20 pairs를 충족했으나 cold와 fixture별 p95는 각각 20 pairs라 tail 분산이 크다.
- **반례·제약:** aggregate median/p95 대부분과 heap tail은 PASS했으므로 “MP4가 전반적으로 느려졌다”는 주장도 이 근거만으로는 성립하지 않는다.
- **결정 영향:** 결과를 PASS로 재분류하거나 좋은 subset만 선택하지 않는다. 현 exact candidate의 AC-713은 PENDING이고 merge/tag/release는 중단한다.

### F-010 — 일반 Preview가 artifact/compositor initializer를 정적으로 당기는 경로는 좁은 지연 후보 A로 분리할 수 있다

- **근거:** SRC-012.
- **내용:** `SlideRenderer`가 `buildVideoDeckArtifactDraft()` 하나를 위해 `videoArtifact.ts`를 정적으로 import하고, 이 모듈이 `videoCompositor.ts`까지 연결한다. 함수 본문을 verbatim으로 import 없는 기존 `videoTypes.ts`로 옮기고 `videoArtifact.ts`에서 re-export하면 public API/schema/artifact bytes를 바꾸지 않고 정적 initializer edge만 제거할 수 있다.
- **신뢰도:** import graph와 변경 범위는 높음, 실제 latency 개선 여부는 미확정. esbuild metafile은 구조 근거이지 성능 결과가 아니다.
- **반례·제약:** single-file bundle bytes는 거의 줄지 않으며 parse/eval 최적화 효과가 noise보다 작을 수 있다.
- **결정 영향:** 후보 A만 low-risk performance correction으로 승인하고 exact same alternating gate를 한 번 재실행한다.

### F-011 — 더 넓은 후보 B나 통계 gate 사후 변경은 현재 근거로 승인할 수 없다

- **근거:** SRC-010, SRC-011, SRC-012.
- **내용:** 최초 결과를 본 뒤 fixture를 제외하거나 표본·threshold·판정 단위를 바꾸면 사전 gate의 의미가 사라진다. 더 넓은 import/build 재구성 후보 B도 기능·Scorecard·번들 위험과 독립 인과가 아직 측정되지 않았다.
- **신뢰도:** 높음(의사결정 절차).
- **반례·제약:** 후보 A가 실패한 뒤 별도 연구 개정과 새 사전 protocol로 B를 조사하는 것은 금지하지 않는다.
- **결정 영향:** 이번 revision은 A 외 제품 성능 변경을 승인하지 않는다. rerun도 원래 protocol과 실패 항목을 그대로 보존한다.

### F-012 — Candidate A는 aggregate 비악화가 확인됐고 owner가 fixture tail을 진단으로 수용했다

- **근거:** SRC-013, SRC-014.
- **내용:** Candidate A의 warm/cold aggregate enable·first Preview·`heapAfterFirst` 여섯 비교는 모두 기존 noise-band 계산 안에서 PASS다. 같은 raw의 fixture-level strict gate 두 건은 FAIL이며 analyzer 파일도 `pass:false`로 보존된다.
- **신뢰도:** aggregate 계산과 artifact identity는 높음. 한 host의 fixture tail을 전체 사용자 경험으로 일반화하는 신뢰도는 제한적이다.
- **반례·제약:** long 2D와 math fixture의 tail/paired CI 실패는 사라지지 않았고, Candidate A가 성능을 개선했다는 증거도 아니다.
- **결정 영향:** 2026-08-05 owner 승인에 따라 AC-713 release gate는 aggregate 여섯 비교로 PASS한다. Candidate A를 유지하고 재측정하지 않으며 fixture 결과는 진단·잔여 위험으로 공개한다.

## Impact analysis

### 제품과 UX

성능 제품 코드를 바꾸지 않으므로 R-002 navigation UX와 deterministic overflow에 새 위험을 만들지 않는다. 릴리스 노트에서 “loading performance improved”라고 주장하지 않는다.

### 아키텍처와 데이터

Candidate C-001은 외부 temp clone에만 있었고 repository source에는 들어오지 않는다. 설정 schema, persisted data, parser, renderer, export contract 모두 현행 유지다.

### 성능과 자원 사용

현재 reference는 같은 환경에서 warm enable median/p95 157.65/234.36ms, warm first preview 356.45/473.63ms, cold-process enable 464.60/639.69ms, cold-process first preview 475.45/617.07ms다. 이는 cross-machine SLA가 아니라 다음 동일환경 비교의 출발점이다.

### 보안과 개인정보

개인 vault를 사용하지 않았다. local SVG 외의 remote resource도 사용하지 않았다. CDP는 loopback 주소에만 bind했다.

### 호환성과 마이그레이션

제품 변경이 없으므로 migration은 없다. 후보를 다시 검토하면 all bundled themes, default/community themes, popout, fullscreen, export와 persisted settings를 별도 matrix로 통과해야 한다.

### 테스트와 관측 가능성

현재 protocol은 제품 instrumentation 없이 외부 marker를 측정한다. shell/engine/audit 세부 attribution이 필요하면 P/E 승인 뒤 bench-only marker를 넣고 production build에서 제거 또는 overhead를 검증해야 한다.

## Recommendations

### REC-001 — 1.1.0에서는 성능 제품 변경을 하지 않는다

- **근거 Finding:** F-003, F-004, F-005, F-007.
- **권고:** C-001 및 그 일부를 제품 source로 복사하지 않고 P-002의 성능 tranche를 “measured candidate rejected; no product change”로 닫는다.
- **채택 조건:** release branch에 candidate diff가 없고 E-002가 summary/raw evidence와 no-change를 기록한다.
- **기각/롤백 조건:** 후보 일부라도 포함하려면 R-004와 P-002를 먼저 개정하고 단독 candidate dual gate를 다시 통과시킨다.

### REC-002 — UX·Scorecard 릴리스는 성능 후보 부재와 무관하게 진행한다

- **근거 Finding:** F-007, F-008.
- **권고:** UX·Scorecard 범위만 출시하고 release note, README, Community 설명에 성능 개선 문구를 넣지 않는다.
- **채택 조건:** 성능 제품 diff가 없고 size cleanup을 runtime latency 개선으로 표현하지 않는다.
- **기각/롤백 조건:** 실제 채택된 별도 후보가 dual gate를 통과하면 그 증거와 정확한 범위만 새 revision에서 기술한다.

### REC-003 — 다음 성능 연구는 후보를 분리하고 내부 marker를 승인된 bench tranche로 만든다

- **근거 Finding:** F-002, F-004, F-007.
- **권고:** selected-theme registration과 settle policy를 단독 비교하고 shell, engine, iframe load, resources ready, audit complete marker를 승인된 bench tranche에서 분리한다.
- **채택 조건:** 새 R/P/E가 instrumentation overhead, production 제거 여부, all-theme/export/popout compatibility를 정의한다.
- **기각/롤백 조건:** 제품 bundle에 검증되지 않은 marker가 남거나 후보 효과를 분리하지 못하면 채택하지 않는다.

### REC-004 — runtime regression gate는 환경 변경 때마다 재baseline한다

- **근거 Finding:** F-003, F-004, F-008.
- **권고:** 같은 protocol에서 최소 20 alternating pairs와 median/p95/MAD/paired interval을 유지하고 runtime·candidate·fixture identity가 바뀌면 rebaseline한다.
- **채택 조건:** 환경 hash/version, cache policy, discarded runs와 failure를 새 artifact에 보존한다.
- **기각/롤백 조건:** Obsidian/Electron 또는 candidate hash가 달라졌는데 이전 threshold를 그대로 쓰는 비교는 무효로 처리한다.

### REC-005 — size, audit, latency를 독립 지표로 유지한다

- **근거 Finding:** F-006, F-008.
- **권고:** `main.js` size는 Scorecard에, enable/preview는 runtime benchmark에, overflow는 geometry acceptance에 각각 둔다.
- **채택 조건:** 계획과 릴리스 문구가 세 지표의 근거와 성공 조건을 별도로 연결한다.
- **기각/롤백 조건:** bytes 감소만으로 loading 개선을 선언하거나 runtime 개선으로 overflow 검증을 생략하는 계획은 허용하지 않는다.

### REC-006 — 후보 A만 적용하고 사전 AC-713 protocol을 그대로 한 번 재실행한다

- **근거 Finding:** F-009, F-010, F-011.
- **권고:** `buildVideoDeckArtifactDraft()`를 본문 변경 없이 `videoArtifact.ts`에서 기존 `videoTypes.ts`로 옮기고 `videoArtifact.ts`가 이를 re-export하게 한다. `slideRenderer.ts`는 `videoTypes.ts`에서 import한다. 그 밖의 artifact/compositor logic, public API/schema, export bytes와 test contract는 변경하지 않는다.
- **채택 조건:** baseline/runtime/fixtures/order/20-pair minimum/median·p95·MAD·paired CI rule을 최초 run과 동일하게 유지하고 warm 200/cold 40 records를 새 exact candidate에서 재수집한다. 기존 raw와 실패 항목도 보존한다.
- **기각/롤백 조건:** 같은 gate가 하나라도 실패하거나 regression suite가 깨지면 A를 되돌리고 AC-713·release를 계속 보류한다. 성공 subset만 재측정하거나 결과를 재명명하지 않는다.

### REC-007 — 후보 B와 통계 protocol 변경은 별도 선행 revision 없이는 실행하지 않는다

- **근거 Finding:** F-009, F-011.
- **권고:** 후보 A의 predeclared rerun이 끝나기 전에 더 넓은 product/import/build 변경이나 gate calibration을 하지 않는다.
- **채택 조건:** B가 필요하면 질문·변경 표면·독립 baseline·사전 통계를 R-004/P-007에 먼저 추가하고 owner 승인을 받는다.
- **기각/롤백 조건:** 최초 결과를 본 뒤의 threshold 완화, fixture 제외, 반복 실행 중 유리한 run 선택은 허용하지 않는다.

### REC-008 — Candidate A를 유지하고 aggregate 비악화를 1.2.0 release gate로 사용한다

- **근거 Finding:** F-009~F-012.
- **권고:** Candidate A의 exact raw·기존 strict FAIL을 보존한 상태에서 warm/cold aggregate enable·first Preview·`heapAfterFirst`만 release blocker로 사용한다. fixture별 p95·paired CI는 진단으로 보고한다.
- **채택 조건:** 여섯 aggregate comparison이 모두 기존 analyzer의 noise-band gate를 통과하고 제품/overflow/export regression suite가 유지된다.
- **기각/롤백 조건:** aggregate 항목 중 하나가 실패하거나 exact candidate가 달라지면 새 측정 없이 결과를 승계하지 않는다. 현 evidence에 대한 추가 rerun, 성능 개선 claim, 후보 B 확장은 하지 않는다.
