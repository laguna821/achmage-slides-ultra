# R-006 — 1.1.0 태그 실패와 1.1.1 forward-fix 릴리스

## Executive summary

- **결론:** `1.1.0` 제품·navigation은 정상이고 원격 태그도 올바른 annotated tag다. 실패 원인은 pinned `actions/checkout@11d5960…`가 tag push의 peeled commit을 로컬 `refs/tags/1.1.0`에 다시 써서 annotated object를 lightweight처럼 보이게 한 뒤, release workflow가 로컬 object type을 검사한 데 있다.
- **안전한 수정:** tag 이름을 정규식으로 검증한 뒤 해당 태그 하나만 `refs/tags/$tag:refs/release-tags/$tag`로 별도 local namespace에 fetch하고, `cat-file` type·직접 commit target·peeled commit·`HEAD`·event SHA를 모두 확인한다. 이 fetch는 checkout이 만든 잘못된 local tag ref조차 덮지 않고 원격 태그도 이동하지 않는다.
- **릴리스 결정:** 이미 고정된 `1.1.0` 태그를 삭제·이동·재생성하거나 attestation을 약화하지 않는다. 후속 PR에서 workflow를 고치고 버전 tuple을 `1.1.1`로 전진시킨 뒤, exact new `main` SHA에 새 annotated tag를 만들어 정상 tag event에서 세 asset·attestation·draft를 생성한다. 이는 P-002의 immutable-tag/`1.1.1` forward-fix 규칙을 실행하는 것이며 제품 UX의 revert가 아니다.
- **기각한 복구:** 후속 `main`에서 `workflow_dispatch`로 옛 `1.1.0`을 checkout하는 방식은 build bytes를 만들 수는 있어도 OIDC provenance의 `ref`·`sha`가 dispatch를 트리거한 새 `main`을 가리킨다. 또한 기존 workflow의 exact-main-head guard와 충돌한다. 이 방식을 쓰기 위해 검증기를 완화하는 것은 tag→source provenance를 훼손하므로 기각한다.
- **남은 불확실성:** GitHub Actions hosted implementation은 바뀔 수 있다. 따라서 `1.1.1` tag 전에 isolated ref rehearsal, exact-candidate Scorecard preview, same-SHA main Governance를 다시 통과시키고 실제 draft의 attestation을 tag SHA/ref로 검증해야 한다.

## Research brief

### 배경과 의사결정

P-002/E-002의 모든 제품·품질 gate와 owner hallway가 끝난 뒤 PR #2를 merge했고, exact `main` SHA `a921c6bd…10af`에 annotated tag `1.1.0`을 push했다. Tag-triggered release run `30832711524`는 checkout 직후 “Release tag must be annotated, not lightweight”로 실패해 build, attestation, draft를 만들지 않았다. 사용자는 navigation의 section/slide 구분이 정상임을 확인하고 릴리스 단계 진행을 승인했으므로, 이 연구가 답할 결정은 제품을 되돌릴지가 아니라 **immutable tag와 provenance를 보존하면서 릴리스를 어떻게 안전하게 전진시킬지**다.

### 핵심 질문

1. 원격 `1.1.0`은 실제 annotated tag인가, 잘못 생성된 lightweight tag인가?
2. checkout 뒤 로컬 tag type이 달라진 정확한 원인은 무엇인가?
3. 원격 tag를 움직이지 않고 runner의 annotated object를 복원할 수 있는가?
4. 후속 `main`의 manual dispatch로 `1.1.0` draft를 만들면 기존 exact-SHA·attestation invariant가 유지되는가?
5. `1.1.1` forward-fix가 제품 기능을 되돌리지 않으면서 기존 release contract를 온전히 지키는가?

### 성공 기준

- remote tag object, peeled commit, failed run의 head SHA와 failure line을 서로 대조한다.
- pinned checkout source에서 annotation 손실 경로를 line-level로 확인한다.
- 실제 공개 origin과 합성 origin에서 targeted fetch의 성공 및 missing/lightweight/mismatch 실패 행렬을 재현한다.
- manual dispatch가 OIDC/source provenance와 exact-main guard를 보존하지 못한다는 반증을 공식 문서·source로 연결한다.
- tag/asset 불변, exact new-main tag, 세 asset, attestation, draft-only를 만족하는 단일 권고와 검증 가능한 planning handoff를 제공한다.

## Baseline and method

- **기준 커밋:** merged `main` 및 peeled `1.1.0` commit `a921c6bd3039e8c1f0194fc473254b4e741610af`; annotated tag object `52a299c6e12e7a37cd2a809450bfaa5a2f618108`.
- **조사 환경:** Windows 11 PowerShell, Git/gh CLI, Node 24; GitHub-hosted Ubuntu failure log와 GitHub REST API. 접근일은 2026-08-04 KST다.
- **로컬/원격 관찰:** `git cat-file`, `git rev-parse`, `git ls-remote`, GitHub git-ref/tag API, `gh run view --log-failed`, release API를 사용했다.
- **재현:** 폐기 가능한 합성 bare origin과 실제 공개 origin의 임시 clone에서 checkout-like `+<peeled-commit>:refs/tags/1.1.0`을 만든 뒤 scoped `git fetch --force --no-tags origin "refs/tags/1.1.0:refs/release-tags/1.1.0"`을 실행했다. 원격 쓰기는 수행하지 않았으며 실제-origin 재현에서도 원래 local `refs/tags/1.1.0`은 `commit`인 채 유지되고 별도 release ref만 `tag`가 됐다.
- **source audit:** pinned checkout의 `src/ref-helper.ts:79-101`, 현재 release workflow와 GitHub OIDC/attestation 공식 자료를 대조했다.
- **방법의 한계:** manual-dispatch attestation을 실제로 생성하지 않았다. 공식 OIDC claim 정의와 pinned/current official source가 ref/sha를 server-minted event identity에서 가져오는 점으로 기각했으며, 불필요하고 잘못된 provenance를 실제로 서명하지 않았다.

## Current-state evidence

| 항목 | 관찰 값 | 판정 |
|---|---|---|
| remote `refs/tags/1.1.0` object type | `tag` | annotated tag |
| remote tag object | `52a299c6e12e7a37cd2a809450bfaa5a2f618108` | immutable object identity |
| peeled commit | `a921c6bd3039e8c1f0194fc473254b4e741610af` | merge된 exact `main` |
| failed run head SHA/event | `a921c6bd…10af`, tag `push` | 제품/tag target 일치 |
| failed step | `.github/workflows/release.yml:49` local `git cat-file -t refs/tags/$tag` | checkout-local representation 오판 |
| release/draft | 없음 | asset·attestation·공개 side effect 없음 |

Pinned checkout의 all-history fetch 뒤 재검사 경로는 tag event에 commit SHA가 있으면 `+${commit}:${ref}`를 반환한다(`actions/checkout` `ref-helper.ts:98-101`). 즉 remote annotated tag object 대신 peeled commit을 destination tag ref에 쓰는 동작이 source와 실제 run 양쪽에서 일치한다. Upstream도 v6.0.2 release에서 tag annotation 보존 수정이 있었음을 명시한다. 현재 저장소는 별도의 최신 v4 pin을 사용하므로 major action 교체보다 단일 scoped fetch를 최소 수정으로 검증한다.

실제 origin 재현에서 checkout-like local ref는 `type=commit`, OID `a921…10af`였다. 별도 `refs/release-tags/1.1.0` fetch 뒤 release ref는 `type=tag`, OID `52a2…8108`, tag의 직접 target type은 `commit`, peeled commit과 `HEAD`는 모두 `a921…10af`였다. 원래 local tag ref는 계속 `commit`이므로 검증 단계가 checkout의 잘못된 ref를 신뢰하거나 덮지 않는다. Fetch는 remote에 write하지 않는다.

## Findings

### F-001 — `1.1.0`은 정상 annotated tag이고 실패는 checkout-local false negative다

- **판정:** 사실/재현.
- **근거:** SRC-001, SRC-002, SRC-003, SRC-004.
- **내용:** GitHub API와 로컬 full fetch는 remote object type `tag`, object `52a299…8108`, peeled commit `a921c6…10af`를 동일하게 보고한다. 실패 run도 같은 peeled commit에서 시작했으나 checkout 후 local ref type만 `commit`이었다. Pinned checkout source의 tag-event refspec이 이 차이를 설명한다.
- **신뢰도:** 높음.
- **반례·제약:** 향후 checkout action 구현은 달라질 수 있으므로 source version과 run ID를 함께 고정한다.
- **결정 영향:** 제품이나 tag 생성 절차를 원인으로 보고 revert·retag하면 안 된다.

### F-002 — 단일 scoped force-fetch가 annotation을 복원하고 나쁜 tag를 fail-closed로 구분한다

- **판정:** 격리 실험.
- **근거:** SRC-004, SRC-005.
- **내용:** tag 이름을 `x.y.z`로 제한한 뒤 `refs/tags/$tag:refs/release-tags/$tag`를 fetch하면 remote object를 격리된 local ref에 복원한다. 이후 `cat-file == tag`, tag header의 직접 target type `commit`, peeled commit == event/HEAD를 모두 검사할 수 있다. Missing tag는 fetch 실패, lightweight tag는 type `commit`, 다른 commit의 annotated tag는 peeled/event/HEAD mismatch로 각각 거부된다.
- **신뢰도:** 높음.
- **반례·제약:** 현재 public repository에서는 `persist-credentials:false` 뒤에도 read-only fetch가 성공한다. Private-repository 일반화는 별도 credential 설계가 필요하지만 본 저장소에는 해당하지 않는다.
- **결정 영향:** release workflow의 기존 security gate를 약화하지 않고 root cause만 최소 수정할 수 있다.

### F-003 — 후속 main의 manual dispatch는 `1.1.0` tag provenance를 보존하지 못한다

- **판정:** 공식 동작과 source에 근거한 반증.
- **근거:** SRC-006, SRC-007, SRC-008, SRC-009.
- **내용:** artifact provenance에는 workflow를 트리거한 ref, commit SHA와 event가 포함된다. GitHub OIDC `ref`는 workflow를 트리거한 ref이고, official attest implementation은 OIDC claims의 `ref`와 `sha`로 resolved dependency를 만든다. 후속 PR merge 뒤 main dispatch는 checkout 대상이 옛 tag여도 provenance는 새 `refs/heads/main`과 새 main SHA다. 현 workflow는 `--source-digest <tag SHA>`와 `--source-ref refs/tags/<version>` 검증 및 write 직전 `main SHA == tag SHA`도 요구하므로 manual recovery는 두 gate와 모두 충돌한다.
- **신뢰도:** 높음.
- **반례·제약:** GitHub가 향후 explicit provenance source override를 공식 제공할 수 있으나 pinned `actions/attest` inputs에는 그런 옵션이 없다.
- **결정 영향:** manual dispatch를 추가하거나 검증기를 완화해 `1.1.0`을 억지로 발행하지 않는다.

### F-004 — `1.1.1` forward-fix만 immutable tag와 exact tag-event attestation을 함께 보존한다

- **판정:** 연구·계획 규칙에서의 결론.
- **근거:** SRC-002, SRC-005, SRC-009, SRC-010.
- **내용:** 새 workflow commit과 version tuple을 exact new main에 병합한 뒤 새 annotated `1.1.1` tag를 push하면 workflow code, product/source commit, tag event OIDC ref/SHA가 다시 같은 identity를 가진다. 기존 same-SHA Governance, three-asset hash, attestation, draft-only guards를 한 줄도 완화할 필요가 없다. `1.1.0`에는 release가 없으므로 asset overwrite도 없다.
- **신뢰도:** 높음; actual post-tag outcome은 GitHub run으로 최종 확인해야 한다.
- **반례·제약:** 버전 번호가 1.1.0에서 1.1.1로 전진하고 새 release notes가 필요하다.
- **결정 영향:** P-003/E-003에서 workflow fix, 1.1.1 tuple/artifact, exact-candidate gates를 실행한다.

### F-005 — forward-fix는 navigation revert가 아니지만 exact candidate 재검증은 필요하다

- **판정:** 사실/검증 요구.
- **근거:** SRC-010, SRC-011.
- **내용:** 실패 run은 product build 전에 중단됐고 현재 branch 기준 제품 UX source에는 새 변경이 없다. 계획된 diff는 release workflow, R/P/E/Register, version tuple, `1.1.1` notes와 deterministic `main.js` 재생성이다. 다만 manifest/version/workflow가 candidate commit을 바꾸므로 prior `1d8fd58` preview만 재사용하지 않고 exact 1.1.1 candidate Scorecard와 product-source equality를 다시 확인한다.
- **신뢰도:** 높음.
- **반례·제약:** rebuild가 `main.js` content를 바꾸면 예상 밖 제품 diff로 간주하고 원인을 조사해야 한다.
- **결정 영향:** 사용자 기능 테스트를 반복 설계하지는 않되 automated acceptance와 exact candidate/release gates를 모두 다시 실행한다.

## Impact analysis

### 제품과 UX

Navigation, section/slide hierarchy, parser, overflow, themes와 settings 동작은 바꾸지 않는다. 사용자에게 보이는 유일한 차이는 release version `1.1.1`이며 release notes에는 `1.1.0` tag가 draft 이전 workflow failure로 공개되지 않았음을 설명한다.

### 아키텍처와 데이터

Runtime architecture, API, schema, vault data와 migration에는 변화가 없다. Local runner tag-ref restoration과 version tuple만 바뀐다.

### 성능과 자원 사용

성능 변경이나 claim은 없다. `main.js` size/hash는 clean build로 다시 측정하며 byte 감소를 성능 향상으로 표현하지 않는다.

### 보안과 개인정보

원격 tag mutation, asset overwrite와 provenance weakening을 금지한다. Fetch 전에 SemVer 정규식으로 refspec injection을 막고, fetch scope를 해당 tag 하나로 제한한다. Attestation은 반드시 tag event의 server-minted SHA/ref로 검증한다.

### 호환성과 마이그레이션

`manifest.minAppVersion`과 desktop-only 정책은 그대로 유지한다. `versions.json`에 `1.1.1: 1.7.2`를 추가하고 기존 `1.1.0` entry는 append-only로 보존한다.

### 테스트와 관측 가능성

합성/actual origin ref matrix, workflow YAML/bash syntax, version tuple, clean build/hash, acceptance:all, lint, audits, preflight, governance, exact candidate Scorecard를 실행한다. Post-tag run에서 source digest/ref, three assets, downloaded hashes, non-prerelease draft를 직접 확인한다.

### 빌드, 배포, 문서

`docs/release/1.1.1.md`를 추가하고 release workflow가 그 exact tag commit에서 읽게 한다. `main.js`는 clean production build 후 committed artifact와 같아야 한다. Tag 전 same-SHA main Governance를 요구하며 draft 검토 전 공개하지 않는다.

## Recommendations

### REC-001 — annotated tag 검사 전에 scoped remote tag fetch를 수행한다

- **근거 Finding:** F-001, F-002.
- **권고:** SemVer 검증 뒤 exact tag refspec만 force-fetch하고 type/peeled/HEAD identity를 기존처럼 검증한다.
- **채택 조건:** actual/synthetic annotated tag PASS, missing/lightweight/mismatch FAIL, remote object/target 불변.
- **기각/롤백 조건:** fetch가 전체 tag namespace를 변경하거나 remote write credential을 요구하면 채택하지 않는다.

### REC-002 — `1.1.0` manual recovery 대신 `1.1.1` tag-event forward-fix를 사용한다

- **근거 Finding:** F-003, F-004.
- **권고:** workflow fix와 1.1.1 tuple/notes/artifact를 새 main에 병합하고 same-SHA green run 뒤 annotated tag를 만든다. 기존 `1.1.0` tag는 그대로 둔다.
- **채택 조건:** product behavior diff 없음, exact candidate Scorecard gate, same-SHA Governance, actual tag ref/SHA attestation과 draft three-asset 검증.
- **기각/롤백 조건:** tag event provenance가 `refs/tags/1.1.1`과 new main SHA를 증명하지 못하면 publish하지 않는다.

### REC-003 — 기존 release guards를 완화하지 않는다

- **근거 Finding:** F-003, F-004.
- **권고:** exact-main-head, tagged Governance, version tuple, deterministic build, three assets, source digest/ref, draft-only와 post-write ref/hash 검증을 모두 유지한다.
- **채택 조건:** workflow diff가 root-cause fetch와 version-independent 문구 외 trust boundary를 바꾸지 않음.
