# R-001 — 업데이트 연구·계획·실행 거버넌스 설계

## Executive summary

- **결론:** 이 저장소에는 기존 연구·계획 기록이나 저장소 전역 에이전트 지침이 없으므로, Markdown 원장을 중심으로 한 Research → Plan → Execution 체계와 Node 기반 정합성 검사를 함께 도입해야 한다.
- **가장 중요한 근거:** 현재 자동화는 태그 기반 배포 하나뿐이고, 계획 또는 근거 문서가 전혀 없다. 빌드·테스트 명령에도 실제 상태와 설명이 어긋나는 부분이 있어 구두 기억만으로 업데이트하면 검증 범위를 과대평가할 위험이 있다.
- **제품 결정에 미치는 영향:** 앞으로의 모든 실질적 업데이트는 완료된 R-ID, 승인된 P-ID, 실제 결과를 기록한 E-ID를 통해 추적한다. 계획은 Finding 단위로 근거를 연결하고 CI는 참조 무결성과 변경 기록 존재 여부를 검사한다.
- **남아 있는 불확실성:** 현존 수용 테스트의 누락 엔트리포인트와 버전 파일 불일치는 이번 거버넌스 부트스트랩의 수정 범위가 아니다. 후속 조사에서 각각 독립적인 R-ID로 다뤄야 한다.

## Research brief

### 배경과 의사결정

향후 여러 종류의 업데이트를 조사할 때 결과가 채팅에 흩어지지 않고, 서로 다른 조사 주제는 `R-001`, `R-002`처럼 분리되며, 계획과 실행이 반드시 그 근거를 참조하게 만드는 저장소 내 운영 체계를 결정한다.

### 핵심 질문

1. 이 저장소에서 장기간 누적 가능하고 사람이 읽기 쉬운 연구 원장의 최소 구조는 무엇인가?
2. 같은 보고서를 갱신할 때와 새 R-ID를 발급할 때의 경계를 어떻게 명시할 것인가?
3. 계획과 실행이 R-ID를 형식적으로만 적는 것을 막고 Finding까지 추적하게 하려면 무엇을 검증해야 하는가?
4. 현재 빌드·배포 구조에서 자동화할 수 있는 게이트와 아직 자동화하면 안 되는 주장은 무엇인가?

### 성공 기준

- 저장소를 새로 연 작업자가 한 진입점에서 필수 흐름을 발견할 수 있다.
- 보고서 ID가 중복 없이 발급되고 Register와 실제 파일이 자동으로 동기화된다.
- 완료 보고서가 출처, Finding, 권고, 계획 인계 정보를 갖췄는지 검사할 수 있다.
- 계획은 하나 이상의 완료 보고서를, 실행은 계획과 동일한 보고서 집합을 참조한다.
- 제품·운영 파일 변경이 있을 때 실행 기록이 같은 변경 세트에 포함되는지 CI에서 검사할 수 있다.
- 기존 테스트가 정상이라는 검증되지 않은 주장을 새 체계가 만들지 않는다.

## Scope

### 포함

- 저장소 전역 에이전트 작업 지침
- Markdown Research Register, 보고서·계획·실행 템플릿
- R/P/E ID 생성과 frontmatter·교차참조·링크·변경 기록 검증
- Pull Request 및 태그 배포에서 실행 가능한 거버넌스 게이트
- 이번 설계 자체를 보여 주는 R-001, P-001, E-001 기준 사례

### 제외

- 슬라이드 렌더링 코드나 사용자 기능 수정
- 수용 테스트 누락 파일 복원과 테스트 커버리지 재설계
- `package.json`, `package-lock.json`, `manifest.json`, `versions.json`의 버전 정책 수정
- 릴리스 노트 자동 생성, 실제 릴리스 수행, 브랜치 보호 설정
- 외부 SaaS 데이터베이스 또는 이슈 트래커 도입

## Current-state evidence

1. 저장소 루트에는 `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `docs/`가 없었다(SRC-001).
2. `.github/workflows/release.yml:1-50`은 `*.*.*` 태그에 반응해 Node 20에서 설치·빌드·attestation·release를 수행하지만 typecheck, acceptance, 거버넌스 검사를 실행하지 않는다(SRC-002).
3. `package.json:6-15`에는 build, typecheck, acceptance 명령이 있으나 연구·계획 기록을 생성하거나 검사하는 명령은 없다(SRC-003).
4. `main.js`는 `.gitignore:4-5` 설명대로 커밋되는 배포 산출물이고, `build/`는 무시된다. 따라서 실행 증거를 `build/`에만 두면 장기 기록이 되지 않는다(SRC-004).
5. 공개 Obsidian 페이지는 현재 버전을 `1.0.3`, 최소 호환 버전을 `1.7.2+`, 플랫폼을 desktop-only로 표시한다. 공개 GitHub README와 로컬 manifest도 같은 제품 정체성을 설명한다(SRC-005, SRC-006).
6. 로컬 `main`과 원격 `main`, `1.0.3` 태그가 같은 SHA를 가리켜 이번 기준선이 사용자가 지정한 최신 공개 소스와 일치함을 확인했다(SRC-007).

## Findings

### F-001 — 현재 저장소에는 지속 가능한 의사결정 기록이 없다

- **판정:** 사실
- **근거:** SRC-001, SRC-002, SRC-003
- **내용:** 연구 보고서, 계획, 실행 기록, 기여 가이드가 모두 없고 자동화는 릴리스에 집중되어 있다. 향후 조사가 채팅에만 남으면 새로운 세션이 과거 근거를 찾을 안정적인 진입점이 없다.
- **신뢰도:** 높음
- **반례·제약:** Git 기록의 커밋 메시지는 일부 의도를 담지만 조사 질문, 반대 근거, 대안, 미해결 사항을 복원하기에는 부족하다.
- **결정 영향:** 저장소 내부에 사람이 읽는 정식 기록과 자동 인덱스가 필요하다.

### F-002 — 단일 Markdown 보고서 계층이 현재 규모와 도구에 가장 잘 맞는다

- **판정:** 추론
- **근거:** SRC-001, SRC-003, SRC-008
- **내용:** 프로젝트가 이미 Git과 Markdown 중심이고 별도 백엔드가 없다. 보고서를 Git에서 버전 관리하면 diff, 리뷰, 링크, 오프라인 접근을 추가 인프라 없이 얻을 수 있다.
- **신뢰도:** 높음
- **반례·제약:** 보고서가 수백 개로 커지면 검색과 통계에는 SQLite나 외부 인덱스가 유리할 수 있다. 현재는 그 복잡성을 정당화할 규모 근거가 없다.
- **결정 영향:** Markdown을 정본으로 두고 Register는 생성 가능한 인덱스로 만든다.

### F-003 — ID 경계는 “키워드 유사성”이 아니라 의사결정 단위로 정의해야 한다

- **판정:** 추론
- **근거:** SRC-008
- **내용:** 같은 하위 시스템에서도 독립적으로 계획·배포할 수 있는 질문은 별도 보고서가 필요하고, 다른 키워드를 쓰더라도 같은 결정의 추가 검증이면 같은 보고서에 누적하는 편이 추적성이 좋다.
- **신뢰도:** 중간
- **반례·제약:** 경계 판단에는 사람이 개입한다. 완전 자동 분류는 질문의 의미를 오판할 수 있다.
- **결정 영향:** 결정 대상, 핵심 질문, 영향 범위, 성공 기준을 동일성 검사로 사용하고 애매하면 새 ID와 `related` 관계를 쓴다.

### F-004 — R-ID 나열만 강제하면 장식적 준수가 가능하다

- **판정:** 추론
- **근거:** SRC-008
- **내용:** 계획이 `R-001 참고`라고만 쓰면 어떤 근거가 어떤 변경을 정당화했는지 검토할 수 없다. Finding → 결정 → 변경 경로 → 검증의 연결이 있어야 연구가 실제 계획을 제약한다.
- **신뢰도:** 높음
- **반례·제약:** 자동 검사는 ID 존재와 상태를 확인할 수 있지만 결정의 논리적 타당성까지 완전 검증하지는 못한다.
- **결정 영향:** 계획 템플릿에 Research traceability 표를 필수로 둔다.

### F-005 — 보고서는 신선도와 기준 커밋을 함께 가져야 한다

- **판정:** 추론
- **근거:** SRC-005, SRC-006, SRC-007
- **내용:** 공개 버전, API, 플러그인 정책, 코드 구조는 바뀔 수 있다. `updated`만으로는 어떤 코드와 외부 상태를 조사했는지 알 수 없으므로 `baseline_commit`, `review_by`, 출처 접근일이 필요하다.
- **신뢰도:** 높음
- **반례·제약:** 과거 완료 계획은 시간이 지나도 당시 근거로서 유효하므로, 유효기한 경과가 역사 기록 전체를 실패 처리해서는 안 된다.
- **결정 영향:** 진행 중인 계획만 최신성 게이트를 적용하고 완료 기록은 보존한다.

### F-006 — 생성과 검증 자동화가 없으면 병렬 작업에서 ID와 인덱스가 갈라질 수 있다

- **판정:** 추론
- **근거:** SRC-008
- **내용:** 두 작업자가 Register의 마지막 번호를 동시에 보고 같은 다음 ID를 선택할 수 있다. 수동 표 수정은 frontmatter와 인덱스 불일치를 만든다.
- **신뢰도:** 높음
- **반례·제약:** 로컬 파일 잠금은 여러 clone 사이의 충돌까지 막지 못한다. Git merge 시 검증 실패로 중복을 발견하고 한쪽 ID를 재발급해야 한다.
- **결정 영향:** 로컬 생성은 배타 잠금과 원자적 쓰기를 사용하고, CI는 전역 유일성과 Register 동기화를 검사한다.

### F-007 — 현재 테스트·배포 상태를 거버넌스 도입과 동시에 “정상”으로 가정하면 안 된다

- **판정:** 사실 및 추론
- **근거:** SRC-002, SRC-003, SRC-009, SRC-010, SRC-011
- **내용:** `acceptance:all` 이름과 실제 실행 범위가 일치하지 않고, 별도 native acceptance 스크립트는 존재하지 않는 TypeScript 엔트리포인트를 참조한다. `package-lock.json`의 루트 버전도 다른 버전 파일과 다르다. 이 문제를 이번 범위에서 수정하지 않은 채 전체 테스트 게이트를 강제하면 거버넌스 도입과 제품 기준선 수리가 섞인다.
- **신뢰도:** 높음
- **반례·제약:** typecheck와 build가 실제로 실패한다는 뜻은 아니다. 문제는 자동화가 보장하는 범위를 현재 이름과 문서만으로 확정할 수 없다는 것이다.
- **결정 영향:** 이번 CI는 거버넌스 검사만 필수화하고, 테스트 기준선 수리는 별도 연구로 분리한다.

### F-008 — 실행 증거는 무시되는 빌드 폴더 밖에 요약되어야 한다

- **판정:** 사실 및 추론
- **근거:** SRC-004
- **내용:** acceptance 스크립트의 상세 결과가 `build/` 아래 생성되면 Git에 남지 않는다. 재현 명령만 적어도 환경 변화로 결과가 달라질 수 있으므로 실행 당시의 핵심 결과를 E-ID 문서에 함께 남겨야 한다.
- **신뢰도:** 높음
- **반례·제약:** 대형 로그나 바이너리를 전부 커밋하는 것은 비효율적이다.
- **결정 영향:** 실행 기록에는 명령, 종료 코드, 요약, 산출물 위치를 남기고 대형 결과는 CI artifact로 취급한다.

### F-009 — 변경 대상 브랜치의 검사기만 실행하면 검사기 자체를 약화해 우회할 수 있다

- **판정:** 사실 및 추론
- **근거:** SRC-012, SRC-013
- **내용:** 일반 `pull_request` workflow는 PR의 workflow와 스크립트를 실행하므로, 같은 PR이 `package.json`, 검사기, workflow를 no-op으로 바꾸면 후보 코드 검사만으로는 자기 보호가 되지 않는다. 반대로 권한이 높은 `pull_request_target`에서 PR 코드를 checkout해 실행하는 방식은 공급망 위험을 만든다.
- **신뢰도:** 높음
- **반례·제약:** 저장소 소유자가 직접 작성한 변경까지 별도 승인하도록 강제하면 1인 유지보수 흐름이 막힌다. 또한 CODEOWNERS의 실제 강제력은 branch protection/ruleset 설정에 달려 있다.
- **결정 영향:** 후보 코드는 read-only `pull_request`에서 검사하되, 별도의 base-branch `pull_request_target` guard는 PR 코드를 checkout하거나 실행하지 않고 변경 파일과 소유자 승인만 확인한다. 태그 릴리스는 같은 커밋의 성공한 Governance check와 이전 릴리스 이후 diff를 모두 요구한다.

## Alternatives considered

| 대안 | 장점 | 단점·위험 | 필요한 검증 | 판정 |
|---|---|---|---|---|
| 채팅 답변과 단일 메모만 사용 | 도입 비용이 거의 없음 | 검색·중복 판단·출처·계획 연결·세션 간 지속성이 약함 | 장기 운영 시 누락률 측정 | 기각 |
| Markdown 문서와 수동 Register만 사용 | 단순하고 읽기 쉬움 | 병렬 ID 충돌, 깨진 링크, 상태·참조 불일치를 늦게 발견 | 수동 리뷰 규율 | 부분 채택 |
| Markdown + 생성기 + 정합성 CI | 사람이 읽기 쉽고 Git 친화적이며 주요 실수를 자동 검출 | 스크립트 유지 비용, 의미적 품질은 여전히 리뷰 필요 | 생성·sync·check와 CI 시나리오 | 채택 |

## Impact analysis

### 제품과 UX

플러그인 런타임 동작은 바뀌지 않는다. 사용자에게 배포되는 `main.js`, `manifest.json`, `styles.css`의 기능 내용도 이번 작업에서 변경하지 않는다.

### 아키텍처와 데이터

새 정본은 `docs/research/reports`, `docs/plans`, `docs/execution`의 Markdown frontmatter다. Register는 보고서에서 파생되므로 충돌 시 보고서 frontmatter가 우선한다. R/P/E ID는 불변 식별자다.

### 성능과 자원 사용

검사는 작은 Markdown 파일을 순회하고 Git diff를 읽는 수준이다. 제품 빌드나 Obsidian 실행에는 포함되지 않는다.

### 보안과 개인정보

보고서에는 토큰, 개인 메일, 로컬 비밀 경로, 사용자 노트 내용을 복사하지 않는다. 외부 출처 URL과 공개 코드 근거만 기록한다. 생성기는 네트워크를 사용하지 않는다.

### 호환성과 마이그레이션

Node 20과 Windows/Linux 경로를 모두 고려해 Node 표준 라이브러리만 사용한다. 기존 코드와 package dependency는 바꾸지 않는다. 과거 의사결정 기록이 없으므로 소급 작성은 요구하지 않는다.

### 테스트와 관측 가능성

`governance:check`가 ID, frontmatter, 필수 섹션, Register parity, 로컬 Markdown 링크, R→P→E 참조, 진행 중인 계획의 연구 신선도를 검사한다. CI에서는 기준 SHA 이후 제품·운영 파일이 바뀌었을 때 같은 변경 세트의 E-ID가 그 경로를 언급하는지도 검사한다.

### 빌드, 배포, 문서

새 GitHub Actions workflow가 PR과 `main` push에서 거버넌스 검사를 실행한다. 태그 릴리스에도 같은 검사를 추가하되, 이번 작업은 기존 수용 테스트를 릴리스 필수 게이트로 승격하지 않는다. README에는 유지보수 흐름 진입점만 짧게 노출한다.

## Recommendations

### REC-001 — Markdown 보고서를 정본으로 하고 Register를 생성한다

- **근거 Finding:** F-001, F-002, F-006
- **권고:** 보고서 frontmatter를 정본으로 삼고 `REGISTER.md`의 표는 스크립트가 재생성하게 한다.
- **채택 조건:** 생성, sync, check가 Windows와 CI에서 같은 결과를 내야 한다.
- **기각/롤백 조건:** 보고서 규모나 협업 충돌이 Git 기반 운영으로 감당되지 않을 때 외부 인덱스를 재검토한다.

### REC-002 — 의사결정 단위로 R-ID를 분리한다

- **근거 Finding:** F-003
- **권고:** 결정 대상·질문·영향 범위·성공 기준이 모두 같을 때만 기존 보고서를 갱신하고, 그렇지 않으면 새 ID와 관계 필드를 사용한다.
- **채택 조건:** AGENTS와 운영 안내에 같은 규칙이 명시되어야 한다.
- **기각/롤백 조건:** 실제 운영에서 과도한 분할 또는 거대한 단일 보고서가 반복되면 기준을 조정한다.

### REC-003 — 계획을 Finding 단위로 추적한다

- **근거 Finding:** F-004, F-005
- **권고:** 계획 템플릿에 `R/F → 결정 → 경로 → 검증` 표와 신선도 검토를 필수로 둔다.
- **채택 조건:** 승인 상태 계획은 완료되고 유효한 연구만 참조해야 한다.
- **기각/롤백 조건:** 없음. 추적성은 이 시스템의 핵심 요구사항이다.

### REC-004 — 생성기, 검증기, CI를 함께 도입한다

- **근거 Finding:** F-006, F-008
- **권고:** 잠금 기반 ID 생성, 원자적 파일 쓰기, 전역 참조 검사, 변경 경로와 실행 기록의 동시 변경 검사를 구현한다.
- **채택 조건:** 현재 기준 사례와 빈/오류 fixture를 이용한 self-test가 통과해야 한다.
- **기각/롤백 조건:** CI 오탐이 정상 업데이트를 반복적으로 막으면 경로 규칙을 좁히되 R/P/E 참조 검사는 유지한다.

### REC-005 — 테스트 기준선 수리는 별도 조사로 분리한다

- **근거 Finding:** F-007
- **권고:** 거버넌스 도입 PR에서 기존 acceptance와 버전 불일치를 수정하지 말고 Register의 후속 후보로 남긴다.
- **채택 조건:** E-001에 미해결 위험이 명확히 기록되어야 한다.
- **기각/롤백 조건:** 거버넌스 검사 자체가 해당 결함 때문에 실행 불가능할 경우에만 최소 수정한다.

### REC-006 — 검사기와 릴리스 게이트에 별도 신뢰 경계를 둔다

- **근거 Finding:** F-009
- **권고:** `pull_request` 후보 검사는 최소 권한으로 실행하고, governance-core 파일 변경은 PR 내용을 실행하지 않는 base workflow와 CODEOWNERS가 저장소 소유자 작성·승인을 확인하게 한다. 태그 릴리스는 해당 SHA의 성공한 Governance check와 이전 태그 기준 diff 검사를 요구한다.
- **채택 조건:** guard workflow는 PR head를 checkout·실행하지 않고 `contents: read`, `pull-requests: read`만 사용해야 한다.
- **기각/롤백 조건:** GitHub 정책 변화로 `pull_request_target`의 안전한 메타데이터 전용 사용이 불가능해지면 조직 ruleset 또는 외부 required workflow로 대체한다.
