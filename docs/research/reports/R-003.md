# R-003 — Community Plugin Scorecard Review 저위험 개선 전략 및 릴리스 게이트

## Executive summary

- **결론:** 공개 Scorecard의 `Review: Caution`은 현재 공개된 `Risk` 때문이 아니다. 최신 공개 릴리스 `1.0.3`의 Review 항목은 `Warnings 222 + Other 3 = 225 issues`, `Risks 0`이다. 225건 중 193건(85.8%)은 `unnecessary type assertion 151 + styles.css의 !important 42`라는 두 반복 패턴이다. 따라서 플러그인 아키텍처나 핵심 Pretext overflow 동작을 바꾸지 않고도 대부분을 줄일 수 있다.
- **권장 전략:** 한 번에 모든 라벨을 없애려 하지 말고, (A) 런타임 무동작 또는 극저위험 타입·콜백·dead-code 정리, (B) lockfile 보안 패치, (C) 시각 회귀 검증을 동반한 CSS specificity 정리, (D) 별도 build 실험으로 bundle size와 dependency 유래 `fs`를 처리하는 순서가 가장 안전하다. A만으로 이론상 171건, B까지 179건을 줄일 수 있다. C, browser build, 아직 찾지 못한 기능보존 size 해법까지 모두 성공하면 산술상 223건 제거가 가능하지만 이는 실증된 경로도 등급 보장도 아니다.
- **점수의 한계:** 2026-08-02에 검토한 공식 자료에서는 `Passed / Satisfactory / Caution / Risks`의 산식·가중치·임계값을 발견하지 못했다. 공식 ESLint도 Scorecard의 일부만 재현한다. 따라서 “N건을 없애면 Passed”를 인수 조건으로 쓰면 안 된다. **동일 candidate commit의 Developer Dashboard preview scan**은 필수 사전 게이트로 사용하되, 공개 릴리스 scan과 완전히 동등하다는 공식 보장은 없으므로 publish 후 public scan을 최종 판정으로 기록한다.
- **보존해야 할 기능:** clipboard write, export용 `requestUrl`, runtime base64는 사용자 요청에 의해 실행되는 실제 기능이다. 공개 detail의 network 28 flagged locations는 번들된 KaTeX parser의 비-HTTP `.fetch()` 명칭에 매핑됐다. 다만 명시적 first-party network API callsite가 export의 `requestUrl` 한 곳이라는 사실이 “제품의 네트워크 경로가 하나뿐”이라는 뜻은 아니다. Tier 3가 켜진 preview의 원격 R2/user override 배경과 Markdown 외부 이미지도 iframe/browser resource load를 일으킬 수 있다. 직접·간접 경로를 모두 정확히 disclosure한다.
- **동적 코드:** Dynamic Code Execution은 자체 overflow audit의 `iframe.contentWindow.eval(...)`과 번들된 `source-map-js`의 `new Function` 두 원인이 겹친다. 자체 `eval`은 deterministic overflow closed loop의 핵심 검증 경로이므로 이번 저위험 Scorecard 정리에서 제거하지 않는다. 한편 in-memory build 실험에서 esbuild를 browser platform으로 전환하면 dependency 유래 `fs`와 `new Function`이 사라지고 79개 render fixture가 동일했지만, 실제 Obsidian live smoke가 없으므로 아직 채택 결론이 아니다.
- **bundle size:** 현재 `main.js`는 5,254,896 bytes다. 이는 5 MiB보다 12,016 bytes, 5,000,000 bytes보다 254,896 bytes 크다. Obsidian 공식 문서는 Sync Standard의 한계를 “5 MB”라고만 쓰며 scanner의 byte 임계값은 공개하지 않는다. 기능보존 해법을 찾는 size tranche에서는 경계만 간신히 넘기기보다 `< 4,900,000 bytes`를 목표로 하되, 현재 그 목표를 달성한 무손실 해법은 없으므로 무조건적 release AC로 삼지 않는다.
- **성능 조사와의 경계:** 작은 bundle은 설치·동기화와 일부 parse 비용에는 유리할 수 있지만, 이 보고서의 실험은 cold start, plugin load, first preview, first render, memory를 측정하지 않았다. **로딩 속도·경량화·eager/lazy import·메모리 최적화는 별도 R-ID(R-004 후보)**로 조사한다. R-003은 Scorecard를 줄이는 과정에서 얻는 저위험 size 이득까지만 다룬다.
- **릴리스 안전성:** 새 버전은 자동 검토되며 실패 시 검색 노출에 영향을 줄 수 있다. UX 연구 R-002의 변경과 본 보고서의 정리를 같은 후보 브랜치에서 통합하더라도 변경을 독립 commit/tranche로 유지한다. version과 committed build artifact를 candidate commit에 먼저 확정하고, 그 exact SHA를 preview scan한 뒤 tag가 같은 SHA를 가리키는지 확인하고 tag checkout에서 draft assets를 build/attest하여 publish한다. 공개 scan은 다시 비교한다.
- **남은 불확실성:** 공개 Scorecard 자체가 work in progress이며 공식 안내도 false positive/negative 가능성을 인정한다. Malware, vulnerable-dependency, obfuscation, network scans의 `not available` disclosure는 저장소에서 고칠 방법이 공개되어 있지 않다. preview scan으로도 근거가 맞지 않으면 commit SHA, lint 결과, dependency graph와 최소 재현을 보존해 `#plugin-dev`에 제기해야 한다.

## Research brief

### 배경과 의사결정

Achmage Slides Ultra는 2026-08-02 현재 Community Plugin 페이지에서 Health는 `Excellent`, Review는 `Caution`으로 표시된다. 기능상 설치가 차단된 상태는 아니지만, 공개 scorecard의 상태 라벨은 사용자가 설치 전에 보는 신뢰 휴리스틱이다. 제품 소유자는 R-002의 Open Slide Preview navigation discoverability 개선을 새 브랜치·새 릴리스로 배포할 때 Review 경고도 최대한 줄이고 싶어 한다. 단, 핵심 아키텍처, deterministic Pretext measurement, overflow-free packing 및 presentation 결과를 점수 때문에 훼손해서는 안 된다.

이 보고서는 다음 의사결정을 가능하게 한다.

1. 공개 Scorecard의 모든 Review 항목은 무엇이며 225라는 수가 어떻게 구성되는가?
2. 각 항목은 자체 코드, vendored Pretext, transitive dependency, 의도된 capability, scanner/platform 상태 중 어디에서 생기는가?
3. 플러그인 아키텍처와 핵심 렌더 의미를 보존하면서 제거 가능한 항목은 무엇인가?
4. 제거 비용과 회귀 위험을 고려한 구현 순서는 무엇인가?
5. 실제 등급을 추측하지 않고 새 branch와 release를 안전하게 검증하는 공식 경로는 무엇인가?
6. Scorecard 정리와 성능·경량화 연구를 어디까지 결합하고 어디서 분리해야 하는가?

### 핵심 질문

1. `Passed`, `Disclosures`, `Risks`, `Warnings`, `Other` 각각의 공개 항목과 개수는 정확히 무엇인가?
2. `225 issues`에 Disclosure가 포함되는가?
3. `Caution`의 공개 산식 또는 경고 수 임계값이 존재하는가?
4. 공식 `eslint-plugin-obsidianmd`로 어떤 항목을 로컬 재현할 수 있고 어떤 항목은 재현할 수 없는가?
5. 151개의 assertion과 42개의 `!important`는 193개의 독립 결함인가, 반복된 몇 개 패턴인가?
6. dependency advisory 8이라는 수는 8개의 고유 취약점인가, dependency path/occurrence인가?
7. `Direct Filesystem Access`, `Dynamic Code Execution`, `28 network calls`, base64, clipboard는 실제 제품 동작인가 dependency/lexical 탐지인가?
8. `main.js > 5 MB`를 기능 삭제나 패키징 아키텍처 변경 없이 해소할 수 있는가?
9. 새 릴리스를 공개하기 전에 동일 commit을 공식 scanner로 검증할 수 있는가?
10. “Scorecard 개선”과 “실제 로딩 성능 개선”을 하나의 연구 성공 기준으로 묶어도 되는가?

### 반증 질문

1. 경고를 많이 제거해도 비공개 가중치 때문에 `Caution`이 유지될 수 있는가?
2. `!important`를 제거해 외부 테마에서 slider가 다시 보이지 않게 되는가?
3. Type assertion을 단순 삭제할 때 타입 안전성이 오히려 약화되는 위치가 있는가?
4. dependency patch가 Marp/Markdown/PostCSS/MathJax 렌더 결과를 바꾸는가?
5. browser-platform build가 headless fixture에는 동일해도 실제 Electron/Obsidian runtime에서 깨지는가?
6. bundle 크기 감소가 실제 plugin load나 first preview를 개선하지 않을 수 있는가?
7. capability를 제거해 점수는 좋아지지만 export 또는 deterministic overflow audit 기능이 퇴행하는가?

### 성공 기준

- 공개 `1.0.3`의 225개 항목이 category 및 rule별 산술로 완전히 reconcile된다.
- 모든 자체 코드 경고에 `path:line` 또는 명확한 symbol이 연결된다.
- vendored, transitive, first-party, intentional capability, platform-unavailable을 구분한다.
- 사실, 관찰, 실험 결과, 추론, 권고를 분리하고 핵심 Finding마다 Source ID를 연결한다.
- 등급 산식, 5 MB threshold, advisory DB drift, false positive 가능성을 숨기지 않는다.
- “아키텍처 비변경” 범위에서 실행 가능한 단계와 보류할 단계를 구분한다.
- 다음 계획이 `F-ID → 결정 → 변경 경로 → 검증`으로 옮길 수 있는 권고와 acceptance 후보를 제공한다.
- 릴리스 전에 공식 preview scan을 요구하고 attestation pass를 보존한다.

## Baseline and method

- **저장소 기준:** `b061ce8c4aa528cb6b909f64a87a78a342b2f1d9`, branch `main`, manifest/package version `1.0.3`.
- **작업트리 상태:** R-001 거버넌스 시스템 구축에서 생긴 미커밋 문서·workflow·package script 변경이 이미 존재한다. R-003은 제품 source/build/release 파일을 수정하지 않았으며, README와 release workflow에 대한 관찰은 해당 선행 변경을 포함한 현재 작업트리를 기준으로 한다. 구현 계획에서는 pristine HEAD와 선행 governance diff를 구분해야 한다.
- **공개 기준:** Community detail page가 가리키는 latest release `1.0.3`; created 2026-06-26, last updated 2026-07-01, 조사 접근일 2026-08-02.
- **조사 환경:** Windows/PowerShell, Node `v24.12.0`, npm `11.6.2`. 조사 시작 당시 package-lock 및 설치 graph는 Marp Core `4.3.0`, Marpit `3.2.1`, js-yaml `4.1.1`, markdown-it `14.1.1`, linkify-it `5.0.0`, postcss `8.5.9`, xmldom `0.9.9`, esbuild `0.24.2`였다.
- **공개 페이지 수집:** Community Scorecard의 접힌 모든 Review details를 열어 제목, count, detail, file/line, package name을 전사했다.
- **로컬 매핑:** `rg`, source inspection, package-lock dependency path, production bundle token provenance, file-size 측정으로 각 항목을 매핑했다.
- **검증 명령:** `npm run typecheck` PASS; `npm audit --json`, `npm outdated --json`, `npm view`, `npm ls --all`; `Get-Item main.js`; esbuild `write:false` metafile 및 render-output hash 비교.
- **실험:** original lock 환경에서 node-platform과 browser-platform in-memory bundle을 비교했고, 79 fixture × MathJax/KaTeX render 결과 hash mismatch가 0인지 확인했다. 정확한 protocol은 본문에 기록했지만 inline script/output artifact를 보존하지 않았으므로 provisional이며 DOM live preview나 Electron smoke를 대체하지 않는다.
- **외부 근거:** Obsidian 공식 blog/help/developer docs, `obsidianmd` 공식 repositories, GitHub Advisory 원문만 규칙·릴리스 사실의 근거로 사용했다. 다른 플러그인 Scorecard는 issue 수만으로 상태가 정해지지 않는다는 관찰 표본으로만 사용했다.
- **재현성 주의:** 조사 중 `npm audit fix --dry-run --json`이 npm 11.6.2에서 예상과 다르게 ignored `node_modules`를 patch 버전으로 바꾸는 부작용이 발생했다. tracked `package.json`, `package-lock.json`, `main.js`는 변하지 않았다. 따라서 dependency/size 실험 수치는 “원래 lock 환경”과 “변경된 ambient node_modules”를 분리해 기록하고, 구현 단계에서는 반드시 `npm ci`로 lockfile 기준 clean install을 만든다.
- **방법의 한계:** Community scanner/backend source는 공개되어 있지 않고 검토한 공식 자료에서 rating formula를 발견하지 못했다. 인증된 owner dashboard preview scan을 이번 조사에서 실행하지 않았고, public Scorecard snapshot은 이후 scanner/advisory DB 변경을 반영하지 않을 수 있다.

### W-012, O-002: filesystem과 dynamic code provenance

production entry dependency graph의 first-party non-test runtime source에는 Node `fs` import가 없다. `src/tests/overflowMatrix.ts`, `src/tests/realnoteCheck.ts`, `src/tests/tier2Dump.ts`와 build scripts에는 `node:fs`가 있지만 release bundle 밖이다. `main.js`의 유일한 `require("fs")`는 번들된 `postcss/lib/previous-map.js`의 source-map file lookup에서 온다. 현재 제품은 문자열 CSS를 처리하므로 그 경로가 실제 사용될 가능성은 낮지만 capability가 번들에 존재하는 것은 사실이다.

1. `src/audit/auditLoop.ts:135`의 `win.eval(buildProbeExpression(tolerancePx))`; same-origin iframe 안에서 실제 rendered DOM의 overflow를 닫힌 루프로 검사하는 first-party 핵심 경로.

### 공식 local lint와 Scorecard의 차이

2026-08-02 공식 `eslint-plugin-obsidianmd` 최신 package는 0.4.1이다. recommended config는 type-aware `typescript-eslint` 설정을 상속하므로 assertion, misused promises, unsafe argument/assignment/member access, unused vars 다수를 로컬 재현할 수 있다. TypeScript parser에 project를 연결하지 않으면 type-aware 결과가 달라질 수 있다.

그러나 공식 plugin의 `obsidianmd/prefer-active-doc`은 recommended에서 `off`인데 공개 Scorecard는 이를 warning으로 표시한다. official lint에는 `no-eval`, `no-new-func`, 조건부 `no-nodejs-modules` 등 일부 source-level capability/security 규칙이 있지만 Scorecard의 종합 capability/disclosure inventory를 재현하지 못한다. CSS, advisory, bundle size, artifact attestation 및 scan availability도 lint 범위 밖이다. 따라서 local gate는 최소 다음 두 층이어야 한다.

1. official recommended + project type information + `prefer-active-doc` overlay + 필요한 CSS/size/audit scripts.
2. candidate branch/tag/commit에 대한 Developer Dashboard preview scan.

2026-08-02에 검토한 공식 blog/docs와 공개 `obsidianmd` source에서는 Scorecard 전용 waiver file, suppress annotation, 공개 appeal form, repository-side scanner 설정을 발견하지 못했다. 공식 lint는 무제한 disable도 제한한다. false positive는 숨기지 말고 공식 `#plugin-dev`에 증거로 제기한다.

이 표에서만 말할 수 있는 것은 Other가 있어도 Passed일 수 있고, Warning 1건부터 Satisfactory가 관찰되며, Risk 또는 매우 많은 Warning이 Caution과 연관된다는 점이다. 종류·심각도·수량 외 다른 factor가 집계될 수 있다는 **추론**은 가능하지만 정확한 경계는 알 수 없다. 경험적으로 Passed를 가장 안전하게 노리려면 Risks 0을 유지하고 Warnings 0에 접근해야 한다. Preview는 사전 근거로, publish 후 public scan은 최종 관찰로 기록한다.

현재 Achmage의 `Caution` page에도 `Add to Obsidian`이 노출된다. 공식 문서는 errors/fails review가 검색·다운로드에 미치는 영향은 설명하지만 `Caution`이라는 public summary label을 review failure와 동일하다고 정의하지 않는다. 따라서 **현재 Caution은 설치 차단과 동의어가 아니며**, 새 후보의 preview scan에서는 summary label과 별도로 errors/fail flags가 없는지를 확인해야 한다.

## Findings

### F-001 — 225는 225개의 독립 보안 결함이 아니다

- **판정:** 사실/관찰.
- **근거:** SRC-001, SRC-009, SRC-010.
- **내용:** 공개 합계는 `Warnings 222 + Other 3`; Risks는 0이다. `Disclosures 6`과 `Passed 5`는 합계에서 제외된다. 193건은 assertion과 한 CSS cluster에서 나온 반복 occurrence다.
- **신뢰도:** 높음.
- **반례·제약:** scanner 내부에서는 occurrence별 가중치가 다를 수 있으며 공개 formula가 없다.
- **결정 영향:** “보안상 심각한 225개”라는 오해를 피하고 반복 패턴 단위로 작업한다.

### F-002 — 공개 산식은 발견되지 않았고 preview scan이 가장 직접적인 공식 사전 경로다

- **판정:** 사실 + 공개 표본에서의 추론.
- **근거:** SRC-002, SRC-004, SRC-006, SRC-014.
- **내용:** 2026-08-02에 검토한 공식 blog/docs와 공개 `obsidianmd` source에서는 Passed/Caution threshold를 발견하지 못했고 local lint와 scanner rule set도 다르다. 공식 dashboard는 branch/tag/commit preview scan을 제공한다. 현재 공개 `Caution`은 `Add to Obsidian`이 보이는 상태이고, 공식 문서도 이 summary label을 review failure와 동일하다고 정의하지 않는다.
- **신뢰도:** 높음.
- **반례·제약:** backend 정책이 이후 공개될 수 있다. Preview와 release scan의 완전한 동등성도 공식 문서에 보장되지 않았고 release asset/attestation 및 advisory DB 시점이 다를 수 있다.
- **결정 영향:** plan AC는 경고 수 예상 대신 exact candidate commit의 preview result를 필수 사전 근거로 포함하고, publish 후 public new-version scan을 최종 결과로 기록해야 한다.

### F-003 — assertion 151건은 가장 큰 zero-runtime 후보이나 vendor maintenance 경계가 있다

- **판정:** 사실 + 권고.
- **근거:** SRC-001, SRC-009, SRC-011.
- **내용:** 147건이 vendored Pretext, 4건이 own code다. 대부분 compile-time only라 runtime JS가 동일해야 한다. 단 iterator result처럼 안전한 구조로 바꿔야 하는 예외가 있고, vendor fork diff가 늘어난다.
- **신뢰도:** 높음.
- **반례·제약:** scanner가 source lines를 다르게 deduplicate할 수 있고 upstream vendor sync 시 conflict가 생긴다.
- **결정 영향:** runtime-erased assertion은 독립 commit으로 AST/type-aware 수정하고 production JS byte/hash parity를 요구한다. Iterator `done` 검사처럼 emitted JS가 필요한 예외는 별도 commit과 behavior test를 사용한다.

### F-004 — `!important` 42건은 한 의도적 compatibility workaround다

- **판정:** 사실/관찰.
- **근거:** SRC-001, SRC-009.
- **내용:** 모두 `styles.css` typography controls이며 주석은 community theme override를 막는 목적을 명시한다.
- **신뢰도:** 높음.
- **반례·제약:** 더 높은 specificity는 상대 theme의 `!important`를 이기지 못할 수 있다.
- **결정 영향:** 삭제가 아니라 selector contract 재설계와 theme visual matrix가 필요하다.

### F-005 — dependency warning은 실제로 갱신해야 하지만 public 8과 현재 audit는 같은 스냅샷이 아니다

- **판정:** 사실/관찰.
- **근거:** SRC-001, SRC-012, SRC-015.
- **내용:** release lock의 5개 package가 public scanner에 노출됐고 현재 advisory DB는 dev esbuild와 추가 xmldom advisory까지 본다. non-force transitive patch 후보가 존재한다.
- **신뢰도:** 중간~높음.
- **반례·제약:** advisory DB와 dependency resolutions는 빠르게 변한다. dry-run의 예상 외 node_modules mutation도 재현성을 흐렸다.
- **결정 영향:** lockfile을 명시적으로 갱신하고 clean install에서 prod/dev audit와 full render acceptance를 분리한다.

### F-006 — 170 warning + 1 Other는 아키텍처 없이 우선 제거 가능하다

- **판정:** 추론/권고.
- **근거:** SRC-009, SRC-011.
- **내용:** assertion 151, Promise 5, activeDocument 5, unsafe 7, receiver assertion 1, globalThis 1, unused function 1은 의미 변경을 최소화해 처리할 수 있다.
- **신뢰도:** 중간~높음.
- **반례·제약:** activeDocument/globalThis는 headless/popout compatibility, promise wrapper는 rejection 처리, dead helper chain은 새 unused 발생을 검증해야 한다.
- **결정 영향:** Phase A로 묶되 runtime-erased assertions, emitted iterator guard, event/type, vendored DOM compatibility를 작은 commit으로 나눈다.

### F-007 — `main.js`는 경계 초과이며 단순 dead-code 정리만으로는 robust budget을 만들지 못한다

- **판정:** 사실/실험.
- **근거:** SRC-008, SRC-010, SRC-013.
- **내용:** current 5,254,896 bytes. unused `transformTables`는 production에서 이미 tree-shake된다. browser build의 30KB 감소도 decimal 5MB 및 4.9MB budget을 충족하지 못한다. MathJax, Highlight.js, embedded assets가 큰 축이다.
- **신뢰도:** 높음(크기), 중간(향후 scanner threshold).
- **반례·제약:** dependency/minifier 버전에 따라 수 KB~수십 KB 변한다.
- **결정 영향:** CI byte budget과 bundle metafile diff를 도입하고, 기능 보존형 size tranche를 별도로 검증한다.

### F-008 — direct fs와 dependency `new Function`은 first-party 의도가 아니라 PostCSS/source-map 경로다

- **판정:** 사실/실험.
- **근거:** SRC-010, SRC-011, SRC-013.
- **내용:** production entry의 first-party non-test runtime source에는 Node fs import가 없고 test/build의 `node:fs`는 release graph 밖이다. release bundle의 fs/new Function은 transitive path다. browser-platform 탐색 실험은 두 token을 제거하고 fixture parity를 유지했다.
- **신뢰도:** 높음(provenance), 중간(채택 안전성).
- **반례·제약:** live Obsidian, custom CSS/source maps, export, Electron compatibility는 미검증이다.
- **결정 영향:** dependency patch보다 build target candidate를 먼저 live-smoke하되, 결과를 size 해법 전체로 과장하지 않는다.

### F-009 — own `eval` 제거는 Scorecard cosmetic cleanup이 아니라 core overflow 변경이다

- **판정:** 사실/권고.
- **근거:** SRC-009, SRC-011, R-002.
- **내용:** `auditLoop.ts:135`는 iframe의 실제 DOM overflow를 검사하는 닫힌 루프에 있다. 제거하려면 execution boundary와 timing을 재설계해야 한다.
- **신뢰도:** 높음.
- **반례·제약:** 같은 document에 typed function을 주입하지 않고도 직접 inspect하는 더 단순한 설계가 가능할 수 있다.
- **결정 영향:** 이번 Scorecard tranche에서 보류하고, 필요 시 독립 research/plan과 deterministic parity AC를 둔다.

### F-010 — network/base64/clipboard는 숨길 대상이 아니라 정확히 설명할 capability다

- **판정:** 사실/관찰/권고.
- **근거:** SRC-001, SRC-003, SRC-009, SRC-011.
- **내용:** public detail의 network 28 flagged locations는 로컬에서 KaTeX의 비-HTTP `.fetch()` 명칭 28곳에 매핑됐다. 명시적 first-party network API callsite는 export의 `requestUrl` 한 곳이지만 Tier 3 remote background와 Markdown external image는 preview iframe/browser가 load할 수 있다. clipboard는 explicit write-only buttons, base64는 self-contained export다.
- **신뢰도:** 높음.
- **반례·제약:** scanner가 다음 버전에서 semantic analysis를 개선하거나 disclosure UI를 변경할 수 있다.
- **결정 영향:** 기능을 제거하거나 우회 API로 숨기지 않고 README와 dashboard disclosure를 구체화한다.

### F-011 — unavailable scan disclosures는 저장소에서 해결할 수 있는 warning으로 보이지 않는다

- **판정:** 관찰.
- **근거:** SRC-001, SRC-002.
- **내용:** malware/dependency/obfuscation/network scan unavailable 항목에 author-side remediation이 공개되지 않았다.
- **신뢰도:** 중간.

- **결정 영향:** 코드 우회를 하지 말고 preview/public scan에서 재확인한 뒤 platform issue라면 공식 채널에 제기한다.

### F-012 — release attestation pass는 보존해야 할 신뢰 자산이다

- **판정:** 사실/권고.

### F-014 — UX와 Scorecard를 같은 release에 넣을 수 있지만 검증 tranche는 분리해야 한다

## Impact analysis

### 제품과 UX

- Phase A는 사용자 기능을 바꾸지 않는 것이 목표다. promise wrapper의 save/render 순서, typed arrays, active document 선택만 보존하면 체감 변화가 없어야 한다.
- CSS tranche는 typography slider의 track/thumb/active/focus 가시성에 직접 영향을 준다. 특히 community theme에서 퇴행할 수 있다.
- clipboard, remote image export, base64를 제거하면 명백한 UX/기능 손실이므로 유지한다.
- Highlight language 제한은 “경량화”이지만 code fence 지원 범위를 줄이는 제품 결정이다.
- R-002 navigation UI는 자체 discoverability 목표와 interaction acceptance가 있으므로 Scorecard 수정과 같은 commit에 뒤섞지 않는다.

### 아키텍처와 데이터

- 타입/assertion/dead code/CSS specificity/lock refresh는 data schema나 slide parsing model을 바꾸지 않는다.
- browser-platform build는 bundle resolution boundary를 바꾸므로 build architecture에는 영향이 있지만 runtime feature architecture를 재설계하지는 않는다.
- asset 외부화, math engine 제거, Marp fork, own eval bridge 재설계는 현 범위의 “아키텍처 비변경”을 넘어선다.
- 저장된 설정 schema, vault markdown, exported HTML contract는 모든 권장 tranche에서 보존되어야 한다.

### 성능과 자원 사용

- 작은 main.js는 disk/sync/download와 parse 비용에 긍정적일 수 있으나 실제 latency 개선은 미측정이다.
- browser-platform 후보의 약 30KB 감소는 성능 개선으로 해석할 정도의 근거가 없다.
- Highlight.js 축소는 약 1MB로 유의미하지만 feature compatibility cost가 있다.
- embedded font/background는 약 1.18MB source payload지만, 별도 asset화가 load/memory를 개선하는지는 R-004에서 측정해야 한다.

### 보안과 개인정보

- known dependency advisories는 실제로 제거해야 하며, prod와 dev dependency를 구분해 audit한다.
- network destination은 bundled default R2 URL, 사용자 Tier 3 override, Markdown external image를 포함한다. Preview에서는 iframe/browser가 resource를 load할 수 있고 export에서는 `requestUrl`이 fetch/inline한다. 각 trigger와 data flow를 문서화한다.
- clipboard는 read가 아니라 user-triggered write다.
- direct fs warning은 dependency의 source-map path이며 first-party local override는 Obsidian `FileSystemAdapter`를 통해 desktop-only 기능으로 공개돼 있다.
- eval은 same-origin presentation iframe audit에 쓰이지만 동적 실행 특성 자체는 맞다. 입력이 어떻게 구성되는지와 외부 untrusted string이 섞이지 않는지를 구현 계획에서 재확인해야 한다.

### 호환성과 마이그레이션

- activeDocument 변경은 popout에는 유리할 수 있으나 `typeof document` guard와 실제 `doc` 선택이 불일치하면 headless/OffscreenCanvas fallback을 깨뜨릴 수 있다.
- Marp transitive patches는 Markdown/PostCSS/parser 결과를 바꿀 수 있다. lock refresh 후 all fixtures와 exported HTML을 비교한다.
- CSS specificity는 Chromium/WebKit pseudo-elements와 Firefox pseudo-elements 모두 유지해야 한다.
- browser build는 desktop-only manifest, Electron runtime, Obsidian external APIs, Node fallback이 필요한지 live test한다.
- data migration은 없어야 한다. settings JSON diff가 생기면 범위 이탈이다.

### 테스트와 관측 가능성

- official lint에 project type info와 `prefer-active-doc` overlay를 추가한다.
- runtime-erased assertion tranche는 production `main.js` SHA-256/byte equality를 가장 강한 no-runtime-change 증거로 쓴다.
- dependency/build tranche는 bundle metafile group diff와 token provenance를 보존한다.
- UI는 default light/dark, 최소 3개 specificity가 강한 community theme, hover/active/focus/keyboard를 캡처한다.
- overflow matrix, native 1920, bidi/CJK/emoji/font-stress, bento/card, wide/long table, both MathJax/KaTeX를 유지한다.
- popout, narrow pane, fullscreen, Tier 3/Markdown external resource preview, remote image export, offline self-contained HTML을 포함한다.
- candidate commit preview scan의 전체 category count와 public release scan을 execution record에 보존한다.

### 빌드, 배포, 문서

- `main.js`는 committed release artifact이며 build 후 diff를 검토한다.
- `< 4,900,000 bytes`를 기능보존 size 후보의 decision target으로 삼고, 그 해법을 채택할 때만 CI hard budget으로 둔다. 달성하지 못하면 기능을 몰래 제거하지 말고 residual warning과 후속 결정을 기록한다.
- release workflow의 source verification과 main.js/styles.css attestation을 보존한다.
- manifest `x.y.z`, release tag, release assets가 일치해야 한다.
- README의 기존 Tier 3/export network disclosure를 실제 trigger/destination과 대조해 정밀화하고, base64 purpose, clipboard write, FileSystemAdapter scope를 보강한다.
- optional `CONTRIBUTING.md`는 Health hygiene 개선이지만 Review 작업과 별도 commit으로 둔다.

## Recommendations

### REC-001 — 목표를 “Passed 보장”이 아니라 “저위험 최대 제거 + 실제 preview 판정”으로 정의한다

- **근거 Finding:** F-001, F-002, F-014.
- **권고:** 계획 성공 기준에 Risks 0 유지, known warnings 최대 제거, deliberate remaining capability rationale, candidate commit preview scan, release scan 기록을 둔다. 공개 산식 추정값을 AC로 쓰지 않는다.
- **채택 조건:** owner dashboard에서 branch/commit preview가 가능함을 확인한다.
- **기각/롤백 조건:** preview 결과를 execution record로 보존할 수 없으면 release를 보류한다.

### REC-002 — Phase A를 네 개의 독립 low-risk commit으로 실행한다

- **근거 Finding:** F-003, F-006.
- **권고:** (A1a) runtime-erased assertions/receiver cast, (A1b) `PretextMeasurementEngine.ts:238` iterator 안전화, (A2) Promise·unsafe types·dead helper, (A3) activeDocument/globalThis로 나눈다. 예상 제거는 warning 170 + Other 1이다.
- **채택 조건:** official type-aware lint, typecheck, acceptance가 통과하고 A1a는 production JS가 byte/hash equivalent다. A1b는 예상한 iterator guard 외 bundle 차이가 없고 cache eviction behavior가 동일하다.
- **기각/롤백 조건:** A1a bundle이 달라지거나 A1b cache behavior 또는 A3 headless/OffscreenCanvas/popout 결과가 달라지면 해당 commit을 분리 재조사한다.

### REC-003 — vendored Pretext 경고는 AST/type-aware 방식으로만 정리한다

- **근거 Finding:** F-003.
- **권고:** regex 일괄 치환을 금지하고 rule autofix diff를 review한다. upstream/vendor provenance와 수정 이유를 주석 또는 vendor sync 기록에 남긴다.
- **채택 조건:** all Pretext unit/overflow/bidi/font fixtures, runtime-erased subset의 bundle byte parity, emitted iterator refactor의 설명 가능한 diff.
- **기각/롤백 조건:** assertion 제거가 inference를 `any`로 약화하거나 upstream sync 비용이 과도하면 first-party 4건만 먼저 처리하고 잔여를 정당화한다.

### REC-004 — dependency lock을 의도적으로 갱신하고 clean environment에서 이중 audit한다

- **근거 Finding:** F-005.
- **권고:** Marp major/fork 없이 현재 declared range 안의 transitive patch를 먼저 시도한다. `npm audit --omit=dev`와 전체 `npm audit`를 분리하고 esbuild major는 별도 build compatibility commit으로 다룬다.
- **채택 조건:** clean `npm ci`, prod advisory 0 목표, typecheck, overflow/native/export acceptance, preview dependency warning 소거.
- **기각/롤백 조건:** renderer output hash/geometry가 달라지고 원인을 수용할 근거가 없으면 lock update를 좁혀 재시도한다.

### REC-005 — `!important`는 selector specificity 재설계와 theme matrix가 준비된 경우에만 제거한다

- **근거 Finding:** F-004.
- **권고:** owner-scoped dedicated classes로 reset/range track/thumb/active/focus를 재작성한다. 42개를 한 CSS component test 단위로 취급한다.
- **채택 조건:** default light/dark + 최소 3개 강한 community theme + keyboard focus/active screenshots PASS.
- **기각/롤백 조건:** theme에서 white-on-white/track loss/focus loss가 한 건이라도 재현되고 warning 일부를 유지하는 것보다 안전한 selector가 없으면 해당 `!important`를 유지하고 rationale를 기록한다.

### REC-006 — size gate는 scanner 경계보다 충분한 headroom을 둔다

- **근거 Finding:** F-007.
- **권고:** `< 4,900,000 bytes`를 기능보존 size tranche의 목표 budget/decision gate로 둔다. 달성 가능한 해법이 승인된 경우에만 CI hard gate로 전환하고 bundle metafile의 group별 증감을 기록한다.
- **채택 조건:** 기능 보존 후보로 target을 달성하고 all acceptance와 preview size warning을 통과한다.
- **기각/롤백 조건:** math engine, rare language, embedded offline asset 기능을 조용히 삭제해야만 달성되면 size warning을 명시적 residual로 남기고 별도 제품 결정/R-004로 올린다.

### REC-007 — browser-platform build를 fs/new Function 제거의 첫 실험 후보로 삼되 바로 채택하지 않는다

- **근거 Finding:** F-007, F-008.
- **권고:** dependency 내부 patch보다 esbuild platform/browser resolution 후보를 먼저 clean lock 환경에서 재현한다. fixture hash 외 live Obsidian, custom CSS/source maps, export, popout을 검증한다.
- **채택 조건:** `require("fs")`와 dependency `new Function` 0, live/fixture parity, external resolution 정상, size budget을 다른 기능 보존 최적화와 함께 달성.
- **기각/롤백 조건:** Electron runtime error, custom CSS/source-map behavior 차이, Obsidian API resolution 문제 발생.

### REC-008 — Highlight language 축소는 Scorecard 수정으로 몰래 포함하지 않는다

- **근거 Finding:** F-007.
- **권고:** robust size margin이 다른 방법으로 불가능할 때만 supported-language policy로 별도 결정한다. rare languages를 plaintext fallback으로 바꾸면 release notes와 tests에 명시한다.
- **채택 조건:** 제품 소유자가 호환성 축소를 명시 승인하고 representative language matrix를 정의한다.
- **기각/롤백 조건:** 기존 full syntax highlighting이 제품 약속이거나 사용 데이터 없이 축소를 정당화할 수 없음.

### REC-009 — own eval은 이번 tranche에서 유지한다

- **근거 Finding:** F-009.
- **권고:** Dynamic Code Execution Other 하나를 줄이기 위해 deterministic audit을 건드리지 않는다. Phase C 후 preview status가 목표에 못 미치고 eval이 결정적 원인으로 확인될 때 별도 research를 만든다.
- **채택 조건:** current input construction과 same-origin boundary를 문서화하고 untrusted code injection이 없음을 후속 검토한다.
- **기각/롤백 조건:** 보안 audit에서 실제 injection path가 발견되면 우선순위를 즉시 올린다.

### REC-010 — capability는 구체적으로 disclosure하고 scanner를 game하지 않는다

- **근거 Finding:** F-010, F-011.
- **권고:** README/dashboard의 기존 문구를 검증·보강하여 export `requestUrl`뿐 아니라 Tier 3 R2/user URL 및 Markdown external resource의 preview browser load까지 destination/trigger/data flow로 적고, clipboard write-only action, base64 self-contained export, FileSystemAdapter local override를 설명한다. KaTeX 28-location mapping 근거를 execution record에 보존한다.
- **채택 조건:** 문서가 실제 코드와 일치함을 source review로 확인한다.
- **기각/롤백 조건:** disclosure 때문에 기능을 숨기거나 custom encoder/API alias를 도입하려는 변경은 금지한다.

### REC-011 — local scorecard preflight를 두 층으로 만든다

- **근거 Finding:** F-002, F-006.
- **권고:** official `eslint-plugin-obsidianmd@0.4.1` pinned config + project typing + `prefer-active-doc` overlay를 도입하고, 별도 CSS `!important`, exact byte size, `npm audit`, bundle token checks를 추가한다. 이것이 actual Scorecard parity가 아님을 문서화한다.
- **채택 조건:** CI 시간이 수용 가능하고 generated/vendor 포함 범위를 실제 scanner와 대조한다.
- **기각/롤백 조건:** local green을 공식 scan green으로 표시하는 오해가 생기면 명칭을 `scorecard-preflight`로 제한한다.

### REC-012 — version/build가 확정된 동일 candidate commit을 preview하고 publish 후 재판정한다

- **근거 Finding:** F-002, F-012, F-014.
- **권고:** version과 committed `main.js`/manifest/styles를 candidate commit에 먼저 확정한다. 그 exact SHA를 preview scan하고 tag가 같은 SHA를 가리키는지 확인한 뒤, tag checkout에서 draft release assets를 build/attest해 publish한다. 공개 후 Scorecard가 새 version을 가리키는지와 preview 차이를 확인한다. Preview가 release-only asset verification과 완전히 동등하다는 가정은 하지 않는다.
- **채택 조건:** preview에 errors/fail flags가 없고 target review 상태 또는 명시 승인된 잔여가 기록되며, publish 후 public scan이 별도로 확인됨.
- **기각/롤백 조건:** tag와 manifest 불일치, asset가 다른 commit에서 생성, attestation 실패, 공개 scan 악화.

### REC-013 — Health hygiene는 Review와 분리해 선택적으로 개선한다

- **근거 Finding:** F-001.
- **권고:** `CONTRIBUTING.md` 추가는 저비용이며 Health hygiene를 완성할 수 있지만 Review 225 문제 해결로 계산하지 않는다.
- **채택 조건:** 실제 contribution/issue/reporting 절차를 담을 수 있음.
- **기각/롤백 조건:** 빈 형식 문서만 만들어 score를 game하게 되는 경우.

### REC-014 — 실제 로딩 속도와 경량화는 별도 R-004 후보로 조사한다

- **근거 Finding:** F-013.
- **권고:** cold plugin enable, warm reload, first Open Slide Preview, first stable render, large document, memory peak/steady state, bundle parse/eval profile를 정의한다. R-003의 metafile은 가설 생성 자료로만 사용한다.
- **채택 조건:** 성능 업데이트를 실제 계획 범위에 넣기로 결정한 경우 새 R-ID를 생성한다.
- **기각/롤백 조건:** bytes 감소만으로 “loading faster”를 선언하는 계획은 허용하지 않는다.
