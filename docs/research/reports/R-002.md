# R-002 — Open Slide Preview 2D 내비게이션 발견 가능성 개선

## Executive summary

- **결론:** 결정론적 파싱과 overflow 분할, `logical group × frame`이라는 2차원 정보구조는 유지한다. 기본 UX는 **선형 읽기 경로와 section 탐색 경로를 함께 제공하는 dual-path navigation**으로 개선하는 것이 가장 타당하다. 즉 초보자는 화면에 보이는 `이전/다음`만 반복해 `2-1 → 2-2 → 2-3 → 3-1`을 한 장도 빠뜨리지 않고 읽고, 숙련자는 명시적인 `이전/다음 섹션`과 keyboard-accessible section path로 섹션을 건너뛴다.
- **가장 중요한 근거:** 현재 코드에는 이미 `nextFrame()`이라는 순차 전진 동작과 `nextLogical()`이라는 섹션 점프가 따로 있지만, 하단 바는 섹션 점프만 노출하고 `N / 전체 섹션`만 표시한다. 세로 점은 stage hover 때만 7×7px로 나타나며, 위·아래 control은 저대비 glyph-only `div`다. 따라서 기능 부족보다 **두 경로의 이름·위계·상태가 UI에 드러나지 않는 것**이 핵심 결함이다.
- **함께 고쳐야 할 입력·접근성 결함:** document-level key handler가 `defaultPrevented`, modifier, interactive target을 구분하지 않아 focused button의 `Space`가 그 button을 누르는 대신 slide를 전진시키고 `Ctrl/Cmd+F`에도 의도치 않은 fullscreen 요청이 함께 발생한다. 또한 현재 group의 보이지 않는 frame들은 시각적으로만 viewport 밖에 있을 뿐 `aria-hidden`이나 `inert`가 없다. 새 navigation shell은 이 두 문제를 acceptance gate로 다뤄야 한다.
- **제품 결정에 미치는 영향:** 하단의 1차 control은 대칭적인 `previousInReadingOrder`/`nextInReadingOrder`, 2차 control은 labeled section jump로 만들고 위치를 `섹션 2/7 · 슬라이드 1/3`처럼 계층적으로 표시한다. Right/Down/PageDown/Space 같은 common Next 입력을 모두 reading order로 보내는 **safe-default dual-path**를 1.1.0 기본값으로 채택한다. 제품 소유자 결정에 따라 one-time coach mark나 tutorial persistence는 추가하지 않고 상시 route state와 help만 제공한다(F-015).
- **남아 있는 불확실성:** interaction profile과 desktop export 범위는 F-015로 결정됐지만 Achmage 신규 사용자 대상 독립 비교 실험은 아직 없다. 따라서 owner hallway와 자동 matrix를 릴리스 gate로 사용하되 인간 이해도 신뢰도는 `medium`으로 유지한다. visible bar의 narrow 축약과 실제 보조기술 노출은 구현 검증이 필요하다.

## Research brief

### 배경과 의사결정

Slides Ultra는 설정된 heading 경계를 logical group으로 만들고, 한 화면을 넘는 내용을 Pretext 기반 측정과 실제 DOM audit로 여러 frame에 결정론적으로 분할한다. 공개 설명은 viewport clipping을 막는 overflow-free 동작을 제품 약속으로 내세우고 제품 소유자도 현행 파싱의 안정성을 이번 업데이트에서 보존하기를 명시했다. 다만 이 UX 조사는 모든 content 보존을 독립 검증하지 않았고, oversized code block의 중간 줄을 명시적으로 생략하는 정책도 있으므로 “어떤 입력에서도 내용 손실 0”을 조사 사실로 확대하지 않는다(SRC-003, SRC-020).

문제는 사용자가 group 내부에 아래 frame이 있다는 사실을 자주 발견하지 못한다는 것이다. 현재 하단 control만 보면 좌우·처음·끝 이동만 있는 평면 deck처럼 보인다. 사용자가 익숙한 `Right`, `PageDown`, 하단 `▶`, 화면 오른쪽 클릭을 쓰면 다음 logical group의 첫 frame으로 이동하여 현재 group의 남은 frame을 건너뛸 수 있다.

이 조사는 파서나 overflow 알고리즘을 재설계하지 않고 다음 제품 결정을 가능하게 한다.

1. 모든 방향키를 선형화할지, 현재의 2D 조작을 유지할지, 또는 두 경로를 병존시킬지 결정한다.
2. 세로 continuation을 화면을 가리지 않으면서 발견 가능하게 만드는 최소 UI를 정한다.
3. keyboard, pointer, exported HTML에서 같은 의미를 제공하기 위한 상태 전이와 접근성 기준을 정한다.
4. 향후 계획이 파싱 안정성을 침범하지 않도록 안전한 변경 경계와 회귀 검증을 정한다.

### 용어

| 용어 | 이 보고서의 의미 | 현재 코드 |
|---|---|---|
| logical group / 섹션 | heading 또는 수동 break로 나뉜 상위 단위 | `gIdx`, `.achmage-logical-group` |
| frame / 섹션 내 슬라이드 | overflow 분할로 생긴 섹션 내부 화면 | `fIdx`, `.achmage-frame` |
| 읽기 순서 | `(0,0) → (0,1) → … → (1,0)`의 평탄 순서 | 현재 `nextFrame()`만 전진 방향 지원 |
| 섹션 점프 | 현재 frame을 건너뛰고 인접 group의 frame 0으로 이동 | `nextLogical()`, `prevLogical()` |
| 2D 위치 | `(gIdx, fIdx)` 좌표 | `groupData`, `frameCountFor()` |

UI 최종 용어는 아직 확정하지 않는다. `logical group`과 `frame`은 구현 용어이고, 사용자 문구 후보는 `섹션/슬라이드`, `장/페이지`다.

### 핵심 질문

1. 현재 input surface별 실제 상태 전이는 무엇이며 어느 경로가 frame을 건너뛰는가?
2. 발견 실패는 파싱 모델의 문제인가, control signifier·상태·설명의 문제인가?
3. 모든 방향키 선형화, 현행 조작 + active cue, dual-path 중 어느 안이 초보자의 완주와 숙련자의 섹션 점프를 함께 보존하는가?
4. UI가 사용할 위치·route 정보는 기존 `slideMap`과 DOM 상태만으로 충분한가?
5. 작은 점이나 색 반전만으로 continuation을 알리는 안은 접근성·긴 deck·계층 표현에 충분한가?
6. hot reload, font reflow, Tier 2, 좁은 Obsidian pane, fullscreen, HTML export가 UX 변경에 부과하는 제약은 무엇인가?
7. 직접 사용자 데이터가 없는 상태에서 어떤 가설과 회귀 조건을 다음 계획의 acceptance criteria로 넘겨야 하는가?

### 성공 기준

- 현재 2D 모델과 모든 input surface의 실제 동작을 코드 근거로 재구성한다.
- 사용자 제안 1, 2와 적어도 하나의 독립적인 제3안을 동일 기준으로 비교한다.
- 권고안이 Pretext, overflow packing, `SlideMapEntry`를 수정하지 않고 구현 가능한지 확인한다.
- 사실, 관찰, 추론, 권고와 직접 검증하지 못한 가설을 구분한다.
- 접근성, export 일관성, hot reload, 테스트 누락과 롤백 조건을 포함한다.
- 다음 계획이 Finding별 결정·변경 표면·검증을 바로 추적할 수 있다.

## Current-state evidence

### 1. 의도된 정보구조와 파싱 경계

1. `examples/master-prompt-ko.md:20-25`는 제품의 저작 모델을 `##`가 좌우 경계이고 그 아래 내용이 세로 frame으로 흐르는 구조로 설명한다. 다만 실제 경계는 고정 `##`가 아니라 `src/settings.ts:231-253`의 `headingDivider` 설정이며 기본값은 `src/settingsDefaults.ts:26-35`의 `[1,2]`다(SRC-002, SRC-003).
2. `src/engine/slideRenderer.ts:91-140`의 pipeline은 Obsidian 변환 → frontmatter → typography → shape template → `splitOverflowingSlides()` → Marp → presentation shell 순이다. `baseFontSize`와 scale은 `src/engine/slideRenderer.ts:103-108`, frame budget은 `src/preprocessor/overflowSplitter.ts:82-89`, block 재패킹은 `src/preprocessor/overflowSplitter.ts:149-198`에서 결정된다(SRC-003, SRC-004).
3. `src/engine/slideRenderer.ts:168-220`은 연속된 같은 logical ID를 한 group으로 묶고 physical slide들을 frame stack으로 만든다. `src/engine/slideRenderer.ts:259-295`는 브라우저 scroll이 아니라 `overflow:hidden` viewport 안에서 stack을 `translateY`한다. 따라서 사용자 표현의 “아래로 스크롤”은 interaction mental model이며 wheel scrolling 구현은 아니다(SRC-004).
4. `src/engine/slideRenderer.ts:691-719`가 frame 순서와 total을 normalize하므로 navigation UI가 필요한 `(group, frame, frameCount)`는 parser 변경 없이 이미 존재한다(SRC-004).

### 2. 현재 input-action matrix

다음 표는 group `g`, frame `f`, 현재 group frame 수 `F(g)`를 기준으로 한 실제 코드 동작이다(SRC-005).

| 입력 표면 | `0 < f < F(g)-1` | `f = F(g)-1` | `f = 0`에서 역방향 | 의미 |
|---|---|---|---|---|
| `ArrowDown` | `(g,f+1)` | `(g+1,0)` | 해당 없음 | 순차 전진, section 경계 통과 |
| `Space`와 `Shift+Space` | `(g,f+1)` | `(g+1,0)` | 해당 없음 | 둘 다 순차 전진; Shift를 구분하지 않음 |
| `ArrowUp` | `(g,f-1)` | `(g,f-1)` | no-op | section 내부 역방향만 지원 |
| `ArrowRight`, `PageDown` | `(g+1,0)` | `(g+1,0)` | 해당 없음 | 남은 frame을 건너뛰는 다음 section |
| `ArrowLeft`, `PageUp` | `(g-1,0)` | `(g-1,0)` | `(g-1,0)` | 이전 section의 top |
| 하단 `▶/◀` | 다음/이전 section top | 다음/이전 section top | 이전 section top | glyph는 평면 prev/next처럼 보이나 section jump |
| stage 오른쪽/왼쪽 40% 클릭 | 다음/이전 section top | 다음/이전 section top | 이전 section top | 보이지 않는 section jump 영역 |
| stage `▼` | `(g,f+1)` | control이 숨겨짐 | `(g,1)` | keyboard Down과 달리 section 경계를 통과할 수 없음 |
| stage `▲` | `(g,f-1)` | `(g,f-1)` | control이 숨겨짐 | section 내부 이동 |
| vertical dot | 지정한 `(g,f)` | 지정한 `(g,f)` | 지정한 `(g,f)` | 현재 section 직접 선택 |

추가 불일치는 다음과 같다.

- `nextFrame()`은 마지막 frame에서 다음 group으로 이어지지만 `prevFrame()`은 group top에서 멈추므로 서로 역함수가 아니다(`src/engine/slideRenderer.ts:506-512`).
- `Home/End`와 first/last button은 group만 바꾼다. 이미 첫/마지막 group에 있으면 `showGroup()`의 same-group branch가 현재 frame을 유지하여 실제 deck 처음/끝으로 가지 않을 수 있다(`src/engine/slideRenderer.ts:426-445,548-551,610-611`).
- key handler의 처리 대상인 Arrow, Page, Space, Home/End, `F`는 modifier를 검사하지 않는다. 따라서 `Ctrl/Alt/Meta+Arrow`가 navigation으로 소비되고 `Ctrl/Cmd+F`에도 fullscreen 요청이 실행되며 Obsidian hotkey bridge로 전달되지 않는다. `F` branch는 `preventDefault()`를 호출하지 않아 browser 찾기가 함께 일어날 가능성은 있지만 shortcut 충돌 자체는 남는다(`src/engine/slideRenderer.ts:532-605`).
- document-level key handler에는 `e.defaultPrevented` 또는 interactive/editable target guard가 없다. focused 하단 button에서 `Space`를 누르면 native button click의 기본 동작이 취소되어 focused action 대신 `nextFrame()`이 실행되고, authored link/button/input이 있다면 그 내부의 Space·Arrow·Page·Home/End도 slide navigation이 가로챌 수 있다. 반면 stage click handler에는 interactive-target guard가 있어 두 event path의 보호 수준도 다르다(`src/engine/slideRenderer.ts:532-614,628-641`).
- wheel, swipe, touch, pointer gesture listener는 없다. frame viewport가 `overflow:hidden`이므로 trackpad wheel도 아무 동작을 하지 않는다(SRC-004, SRC-005).

### 3. 발견 가능성을 낮추는 현재 UI

1. 하단 56px bar는 `⏮ ◀ N/M ▶ ⏭ Full`만 렌더하며 위/아래, 현재 frame, section 내부 잔여량을 표시하지 않는다(`src/engine/slideRenderer.ts:350-408`). 이 전용 row가 slide를 덮지 않는 장점은 있다(SRC-005).
2. `updateUI()`는 `frameCount`를 계산하면서 counter에는 `gIdx + 1 / totalGroups`만 기록한다. frame을 이동해도 하단 숫자는 변하지 않는다(`src/engine/slideRenderer.ts:466-480`).
3. vertical dots는 stage hover 때만 opacity 1 container가 되고, 각 점은 7×7px, 기본 색은 `rgba(...,0.2)`다. active dot도 scale 1.3에 그친다(`src/engine/slideRenderer.ts:327-348`).
4. `▲/▼`는 stage 우측 하단의 18px glyph, 기본 alpha 0.3이고, 하단 bar와 시각적으로 분리되어 있다(`src/engine/slideRenderer.ts:313-325,390-408`).
5. vertical arrow와 dots는 `div onclick`이며 `role`, `tabindex`, `aria-label`이 없다. 하단 native button 중 네 navigation button도 glyph 외의 descriptive accessible name이나 tooltip이 없다. fullscreen button에는 visible text `Full`이 있다(`src/engine/slideRenderer.ts:390-408,483-497`). `.v-ind.hidden`은 `opacity:0; pointer-events:none`만 적용하므로 visual availability와 접근성 노출을 동기화하지 않는다(`src/engine/slideRenderer.ts:313-325`).
6. `groupData`에는 title과 frame 수가 이미 있고 `updateUI()`는 현재 group data를 읽지만 표시하지 않는다(`src/engine/slideRenderer.ts:413-480`). 데이터 부족이 아니라 표현 누락이다.
7. `README.md:31-37`, `examples/README.md:5-24`, `examples/demo-ko.md:1-20`과 실제 공개 Community Plugin Usage는 preview와 overflow continuation을 설명하지만 실제 2D key grammar나 아래 이동 방법은 안내하지 않는다(SRC-008, SRC-020).
8. preview view와 renderer에는 iframe으로 keyboard focus를 명시적으로 옮기는 `.focus()` 호출이 없고 iframe 생성 시 `title`도 지정하지 않는다. Obsidian이 view open 뒤 어느 document에 focus를 두는지는 실제 앱에서 확인하지 않았으므로, “preview를 연 직후 클릭 없이 방향키가 동작하는가”와 iframe의 accessible name은 별도 재현·보강이 필요하다(`src/view/slidePreviewView.ts:102-109`)(SRC-005, SRC-006).
9. 하단 first/previous/next/last button에는 현재 위치에 따른 `disabled` 또는 route availability 상태가 없다. deck 경계에서도 계속 활성처럼 보이지만 no-op이고, `End`/last는 마지막 group의 frame 0에 머물 수 있어 control의 이름·상태·도착점이 일치하지 않는다(`src/engine/slideRenderer.ts:466-480,548-551,607-612`).
10. 현재 group의 모든 `.achmage-frame`은 한 stack 안에 계속 렌더되고 transform으로만 이동한다. current frame 외 항목에 `display:none`, `aria-hidden`, `inert`가 없으므로 화면 밖 내용이나 link가 접근성 트리·탭 순서에 남을 수 있다. DOM 속성 부재는 사실이지만 실제 screen reader별 노출은 아직 재현하지 않았다(`src/engine/slideRenderer.ts:191-205,265-290,453-463`).
11. 세로 이동의 `transform` transition과 가로 group 전환의 `enterRight`/`enterLeft` animation은 각각 0.3초이며 `prefers-reduced-motion` 분기가 없다(`src/engine/slideRenderer.ts:272-310`). 새 coach mark만 정적으로 만들어도 기존 navigation motion은 그대로 남는다.

### 4. 실제 bundled deck 관찰

정규식 계수로 저장소의 self-contained demo HTML을 확인했다(SRC-009).

| deck | logical groups | physical frames | multi-frame groups |
|---|---:|---:|---:|
| English demo | 43 | 47 | 4 |
| Korean demo | 42 | 46 | 4 |

재현에 사용한 정확한 파일과 계수 명령은 다음과 같다.

```powershell
$paths = @(
  'examples/Achmage Slides Ultra Demo (English).slides.html',
  'examples/Achmage Slides Ultra 사용법 데모.slides.html'
)
$rows = foreach ($p in $paths) {
  $s = Get-Content -Raw -LiteralPath $p -Encoding utf8
  [pscustomobject]@{
    Path = $p
    Groups = ([regex]::Matches($s, '<div class="achmage-logical-group"')).Count
    Frames = ([regex]::Matches($s, '<div class="marpit achmage-frame"')).Count
    MultiFrameGroups = ([regex]::Matches($s, 'data-frames="(?:[2-9]|[1-9][0-9]+)"')).Count
  }
}
$rows | Format-Table -AutoSize
```

즉 2D 상태는 stress fixture에만 존재하는 가상이 아니라 사용자에게 제공되는 demo에도 실제로 나타난다. 바깥 status가 표시하는 `deck.slideCount`는 physical frame 수이고 하단 counter는 logical group 수라 같은 deck을 두 숫자 체계로 표현한다(`src/engine/slideRenderer.ts:140,472-473`, `src/view/slidePreviewView.ts:363-367`).

### 5. render lifecycle, export, test 경계

1. live preview는 re-render 전에 iframe의 numeric `gIdx/fIdx`를 읽고 새 HTML의 restore option으로 넘긴다(`src/view/slidePreviewView.ts:303-360`). 새 topology에서는 index를 clamp할 뿐 같은 content block을 추적하는 stable ID는 없다(`src/engine/slideRenderer.ts:643-681`)(SRC-006).
2. base font 변경은 frame budget과 packing을 바꿀 수 있으므로 동일한 `fIdx`가 re-render 뒤 다른 문장 범위를 가리킬 수 있다. 이 문제를 content identity 재설계로 확장하면 UX-only 경계를 넘는다(SRC-003, SRC-006).
3. live preview와 export는 모두 `SlideRenderer.render()`의 같은 `buildPresentationHTML()`을 사용한다. shell UX를 바꾸면 별도 mode flag가 없는 한 exported `.slides.html`에도 적용된다(`src/view/slidePreviewView.ts:338-396`)(SRC-006).
4. closed-loop audit는 iframe `srcdoc`을 최대 여러 번 교체하고 측정 중 모든 group/frame을 노출했다가 transform을 복구한다(`src/audit/auditLoop.ts:69-103`, `src/audit/overflowProbe.ts:33-91`). HUD는 `.achmage-frame section` 바깥 shell 상태에서 순수 파생되어야 한다(SRC-007).
5. current acceptance harness는 real Chromium geometry와 16/28/40pt를 검사하지만 keyboard, button, transition, aria state는 검사하지 않는다(`src/tests/overflowMatrix.ts:1-16,64-99,247-305,419-490`). navigation 전용 test script도 없다(`package.json:6-23`)(SRC-007).
6. Tier 2 list pagination은 `(cont.)`와 `---`를 생성해 일부 continuation을 같은 group의 vertical frame이 아니라 별도 horizontal group으로 만든다(`src/preprocessor/shapeTemplates.ts:1146-1200,1487-1526`). 새 HUD는 heading이나 `(cont.)` 문자열을 재해석하지 말고 최종 `groupData`/DOM을 정본으로 써야 한다(SRC-003).
7. Community plugin이 실행하는 committed artifact는 `main.js`다. `main.js:6104-6111,6325-6370,6423-6505`를 정적 대조한 결과 frame stack, counter, key mapping, endpoint button handler가 조사한 TypeScript와 일치한다. 따라서 위 navigation 관찰은 source-only 가설이 아니라 현재 배포 artifact에도 들어 있다(SRC-021).
8. baseline부터 존재하는 `acceptance:native-1920-v5` package script는 `scripts/render-native-1920-v5-acceptance.mjs:36-38`에서 없는 `src/tests/renderNative1920V5Acceptance.ts`를 entry로 지정한다. 2026-08-02에 `npm.cmd run acceptance:native-1920-v5`를 직접 실행한 결과 esbuild가 해당 절대 경로를 resolve하지 못해 exit 1로 종료했다. 즉 package entry 자체가 없는 것이 아니라 참조 대상 test source가 누락된 상태다(SRC-007).

## Findings

### F-001 — 핵심 결함은 파싱이 아니라 두 번째 축의 signifier와 상태 누락이다

- **판정:** 사실 및 추론
- **근거:** SRC-001, SRC-003, SRC-004, SRC-005
- **내용:** renderer는 logical group과 frame을 명시적으로 유지하고 순차 전진 함수도 갖고 있다. 그러나 하단 control과 counter가 group 축만 노출하여 사용자가 평면 deck으로 오인하기 쉽다. 제품 소유자가 관찰한 “아래가 있는지 모름”은 코드 구조와 일치한다.
- **신뢰도:** 높음
- **반례·제약:** 실제 신규 사용자별 실패율과 첫 행동은 측정하지 않았다. 일부 사용자는 우측 arrow나 dots만으로도 구조를 발견할 수 있다.
- **결정 영향:** parser·packing을 건드리지 말고 presentation shell의 control hierarchy, route cue, position status를 바꾼다.

### F-002 — 현재 navigation grammar는 input별·방향별로 비대칭이며 조용한 content skip을 허용한다

- **판정:** 사실
- **근거:** SRC-005, SRC-021
- **내용:** Down/Space만 reading order를 전진하고 Right/PageDown/하단 ▶/오른쪽 click은 section top으로 점프한다. Up은 Down의 역함수가 아니며 stage ▼는 keyboard Down과 달리 section 경계를 통과하지 못한다. 같은 glyph와 “다음처럼 보이는” 입력이 서로 다른 범위를 이동한다. first/last도 정확한 deck endpoint를 보장하지 않고 모든 하단 endpoint control이 경계에서 활성처럼 남는다.
- **신뢰도:** 높음
- **반례·제약:** section skip 자체는 의도된 고급 기능이며 제거 대상이 아니다. 문제는 기능이 아니라 명명과 input mapping의 숨은 차이다.
- **결정 영향:** `reading-order previous/next`, `section previous/next`, `local frame up/down`, `deck first/last`를 별도 operation으로 정의한 뒤 모든 surface를 명시적으로 매핑해야 한다.

### F-003 — 현재 counter와 controls는 2D 위치를 설명하지 못하고 접근 가능한 이름도 부족하다

- **판정:** 사실
- **근거:** SRC-005, SRC-008, SRC-009, SRC-020, SRC-021
- **내용:** frame을 이동해도 `N / totalGroups`가 그대로이고, physical slide count와 logical count도 서로 다르다. hover-only 7px dots와 저대비 glyph는 “아래에 더 있음”, 현재 local 위치, 다음 action을 설명하지 않는다. endpoint button의 disabled/available 상태도 없고 공개 Usage에도 key grammar가 없다.
- **신뢰도:** 높음
- **반례·제약:** 최소 UI를 선호하는 발표 화면에서 영구적인 큰 설명은 content 집중을 해칠 수 있다.
- **결정 영향:** 영구 UI는 compact한 계층 counter와 semantic controls로 제한하고, 학습 설명은 조건부로 제공한다.

### F-004 — 파서 변경 없이 shell-only UX 개선이 가능하다

- **판정:** 사실
- **근거:** SRC-003, SRC-004, SRC-005, SRC-006, SRC-007
- **내용:** `groupData`, `gIdx`, `fIdx`, `frameCountFor()`, `totalGroups`에 route와 위치 표시를 계산할 정보가 이미 있다. 안전한 주 변경 표면은 `src/engine/slideRenderer.ts:222-685`의 inline shell이며, 필요할 경우 tutorial persistence만 `SlidePreviewView`가 보조한다.
- **신뢰도:** 높음
- **반례·제약:** content-based hot-reload anchor, Tier 2 continuation 방향 통일, active-file state reset은 shell-only로 완전히 해결되지 않는다.
- **결정 영향:** `splitOverflowingSlides`, `SlideMapEntry`, frame DOM hierarchy, audit selector를 비변경 불변조건으로 둔다.

### F-005 — 공통 Next 입력의 선형화는 유력하지만 section jump를 pointer-only로 만들 필요는 없다

- **판정:** 추론
- **근거:** SRC-001, SRC-012, SRC-019, SRC-022
- **내용:** PowerPoint 같은 flat deck은 Right/Down/PageDown/Space를 모두 Next로 사용하므로 선형화가 친숙하고 사용자가 제기한 “무지성으로 눌러도 누락 없이 전진”을 직접 해결한다. 다만 Achmage에는 실제 2D 구조와 section skip 가치가 있다. 사용자 안 1처럼 모든 common key는 선형인데 이름 없는 좌우 click/button만 section jump로 남기면 modality별 의미가 갈리고 keyboard direct path가 약해진다. 그러나 이것은 선형화의 필연이 아니다. common Next/Previous는 reading order로 보내면서 labeled section buttons와 충돌 검증을 거친 별도 section shortcut을 병존시킬 수 있다.
- **신뢰도:** 중간
- **반례·제약:** 모든 arrow의 공간 의미를 바꾸면 기존 사용자의 muscle memory가 깨질 수 있다. 반대로 Right/PageDown을 section jump로 유지하면 flat-deck 관습에 의존하는 신규 사용자의 silent skip이 계속될 수 있다.
- **결정 영향:** dual-path architecture 안에서 arrows를 공간 이동으로 보존하는 **spatial dual-path**와 common Next/Previous까지 reading order로 통일하는 **safe-default dual-path**를 함께 prototype한다. 어느 쪽이든 section navigation은 labeled pointer control과 keyboard-accessible path 양쪽에 보존한다.

### F-006 — 점 확대나 색 반전만으로는 계층·route·조작법을 충분히 전달하지 못한다

- **판정:** 추론 및 기준 대조
- **근거:** SRC-015, SRC-016, SRC-018
- **내용:** Apple HIG의 page control은 dots를 flat ordered list용으로 설명하고 hierarchy 표현에 부적합하며 약 10개를 넘으면 세기 어렵다고 한다. WCAG는 색을 정보의 유일한 수단으로 쓰지 말고 meaningful control/state가 인접 배경과 3:1 대비를 갖도록 요구한다. 따라서 굵기나 glow는 보조 강조일 뿐, `↓`, 남은 수, 문구, disabled state, accessible name 중 하나 이상이 함께 필요하다.
- **신뢰도:** 높음
- **반례·제약:** Apple HIG는 macOS Obsidian의 직접 규범이 아니고, WCAG target exception 때문에 현재 7px dots가 곧바로 전체 conformance 실패라고 단정할 수는 없다.
- **결정 영향:** dots는 secondary locator로만 두고 primary affordance로 승격하지 않는다. 색 상태에는 shape/text/number를 함께 사용한다.

### F-007 — 가장 강한 제3안은 선형 읽기와 section 탐색을 병존시키는 dual-path navigation이다

- **판정:** 추론
- **근거:** SRC-002, SRC-005, SRC-012, SRC-013, SRC-014, SRC-022
- **내용:** reveal.js 기본 vertical-slide model은 Left/Right로 top-level, Up/Down으로 vertical stack, Space/N/PageDown으로 모든 slide를 semantic reading order대로 통과시키고 Shift+Space/P/PageUp으로 되돌아간다. directional `left/right/up/down`과 semantic `prev/next` operation의 분리는 Achmage의 기존 `nextLogical()`과 `nextFrame()`에 대응한다.
- **신뢰도:** 중간~높음
- **반례·제약:** reveal.js의 built-in visible arrows는 directional이며 두 개의 visible control 세트를 제공하지 않는다. 따라서 “sequential과 section button을 둘 다 보인다”는 것은 reveal.js가 검증한 UI가 아니라 Achmage용 설계 추론이다. control을 같은 무게로 나열하면 오히려 복잡해질 수 있다.
- **결정 영향:** operation은 분리하되 visible hierarchy는 sequential Prev/Next를 1차, labeled section skip을 2차로 prototype하고, 첫/끝·fullscreen 같은 저빈도 action은 responsive grouping이나 overflow를 검토한다.

### F-008 — just-in-time cue와 계층 counter가 영구적인 큰 UI보다 적합하다

- **판정:** 추론
- **근거:** SRC-001, SRC-011, SRC-012, SRC-013
- **내용:** reveal.js는 vertical stack을 처음 만났을 때 down arrow를 bounce하는 `controlsTutorial`을 기본 제공하고, slide number를 horizontal.vertical 또는 flattened 형식으로 표시할 수 있다. Achmage에는 첫 multi-frame group에서 `↓ 이 섹션에 2장 더 있음`을 primary Next에 붙이고, 항상 `섹션 2/7 · 1/3`을 compact하게 표시하는 조합이 대응된다.
- **신뢰도:** 중간
- **반례·제약:** timer-only hint는 놓칠 수 있고 re-render마다 반복되면 성가시다. WCAG 2.2 SC 2.3.3 `Animation from Interactions`는 Level AAA이므로 여기서는 AA 충족 주장보다 motion-sensitive 사용자를 위한 상위 접근성 기준·best practice로 적용한다. 현재 frame transform과 group-enter animation도 함께 검토해야 한다.
- **결정 영향:** cue는 최초 multi-frame encounter에서 action을 수행할 때까지 유지하고, dismiss/help 재호출을 제공하며, motion 없이도 의미가 보이게 한다. `prefers-reduced-motion: reduce`에서는 cue뿐 아니라 모든 비필수 navigation transition과 group-enter animation을 제거한다.

### F-009 — semantic native button, 충분한 hit area, 색 외 상태, focus와 announcement가 필요하다

- **판정:** 기준 대조 및 권고
- **근거:** SRC-014, SRC-015, SRC-016, SRC-017, SRC-018, SRC-023
- **내용:** WAI Carousel Pattern은 native Prev/Next button과 meaningful slide name/position을 권하고 많은 dot가 각각 tab stop이 되는 방식은 keyboard 사용자에게 불리하다고 설명한다. WCAG 2.2는 pointer target 24×24 CSS px 또는 충분한 spacing/equivalent, meaningful non-text state 3:1 contrast, 일반 크기 text 4.5:1 contrast, keyboard operation, color 외 cue를 요구한다. visible glyph는 작게 유지하면서 transparent padding으로 hit target을 넓힐 수 있다. 다만 APG carousel은 평면 item 집합의 예시이므로 nested 2D slide 전체에 그 role 구조를 그대로 복사하지 않고 control semantics와 short name/position-announcement 원칙만 차용한다.
- **신뢰도:** 높음
- **반례·제약:** 전체 WCAG conformance 판정은 실제 DOM, computed contrast, spacing, equivalent control을 test해야 한다. 이 보고서는 설계 기준만 정한다.
- **결정 영향:** clickable `div`를 native button 또는 동등한 semantics로 바꾸고 descriptive label, disabled/available state, focus-visible, iframe accessible name, polite한 `section title + 2/7 · 1/3` feedback를 검증한다. visual hidden/disabled와 accessibility state도 함께 갱신한다.

### F-010 — live preview와 export의 공용 shell, audit re-render, font reflow가 UI 상태 설계의 제약이다

- **판정:** 사실
- **근거:** SRC-003, SRC-006, SRC-007, SRC-020
- **내용:** shell 변경은 기본적으로 export에도 전파되고, audit는 같은 iframe을 여러 번 교체하며, font size는 frame topology를 바꿀 수 있다. tutorial state를 iframe local 변수에만 두면 audit/hot reload 때 재등장할 수 있고 numeric restore는 동일 content anchor를 보장하지 않는다.
- **신뢰도:** 높음
- **반례·제약:** 대부분의 deck은 audit pass 0에서 끝나며 group heading이 유지되면 numeric restore가 실용적으로 충분할 수 있다.
- **결정 영향:** HUD는 render state에서 재생성하고, tutorial-seen persistence와 preview/export 동일성은 계획에서 명시적으로 결정한다. stable content ID는 이번 범위에서 제외한다.

### F-011 — navigation 회귀를 막을 자동 test와 직접 사용성 evidence가 현재 없다

- **판정:** 사실
- **근거:** SRC-001, SRC-007, SRC-009
- **내용:** real-browser overflow harness는 강하지만 navigation transition과 a11y를 검사하지 않는다. bundled demo가 multi-frame topology를 실제 포함해도 그 경로의 reachability assertion은 0건이다. 제품 소유자의 관찰은 문제 존재를 지지하지만 대안별 성공률은 알려 주지 않는다.
- **신뢰도:** 높음
- **반례·제약:** 정적 코드 검토만으로도 현재 transition은 결정적으로 알 수 있다. 모르는 것은 새 UI의 인간 이해도다.
- **결정 영향:** 구현 계획은 pure transition test + browser DOM/a11y test + 작은 비교 사용성 test를 모두 포함해야 한다.

### F-012 — current model의 인접 불일치는 한 UX 변경에 모두 흡수하면 안 된다

- **판정:** 사실 및 범위 판단
- **근거:** SRC-003, SRC-006, SRC-007
- **내용:** Tier 2 continuation은 horizontal group이 될 수 있고, active file 전환·font reflow의 numeric restore가 다른 content를 가리킬 수 있다. 또한 `acceptance:native-1920-v5` script는 존재하지만 그 entry source `src/tests/renderNative1920V5Acceptance.ts`가 없어 실제 명령이 esbuild resolution error로 실패한다. 이들은 navigation discoverability와 연관은 있지만 각자 별도 소유권·성공 기준을 가진다.
- **신뢰도:** 높음
- **반례·제약:** navigation test를 만들기 위해 누락 harness의 최소 대체가 필요할 수 있다.
- **결정 영향:** 새 범위가 필요하면 R-002를 조용히 확장하지 말고 관련 연구를 새 R-ID로 발급한다.

### F-013 — global key handler가 control의 native keyboard 동작과 host shortcut을 침범한다

- **판정:** 사실
- **근거:** SRC-005, SRC-017, SRC-021, SRC-022
- **내용:** handler는 document bubble 단계에서 대부분의 mapped navigation key를 곧바로 `preventDefault()`하고 target·modifier·`defaultPrevented`를 검사하지 않는다. 그래서 focused button의 `Space`는 그 button을 activate하지 않고 reading order를 전진하며, `Ctrl/Cmd+F`에도 fullscreen 요청이 발생한다. `F` branch는 default를 취소하지 않아 browser 찾기가 함께 실행될 수 있지만 host bridge에는 전달되지 않는다. authored interactive content가 있으면 slide와 content가 같은 key를 놓고 충돌할 수 있다.
- **신뢰도:** 높음
- **반례·제약:** 일반 static deck에는 form control이 드물고 Enter는 현재 handler가 처리하지 않아 native button activation이 가능하다. 그러나 navigation bar 자체가 native button이므로 Space 충돌은 별도 authored content 없이도 발생한다.
- **결정 영향:** key mapping보다 먼저 event ownership 규칙을 정한다. `defaultPrevented`, interactive/editable target, exact modifier 조합을 guard하고 focused control의 Enter/Space는 native activation에 맡긴다. reveal.js 6.0.1처럼 `N/P`를 semantic next/previous 후보로 포함하고 이 동작을 real-browser focus test로 고정한다.

### F-014 — inactive frame은 시각적으로만 가려져 접근성·focus 상태가 current frame과 분리되지 않는다

- **판정:** DOM 사실 및 위험 추론
- **근거:** SRC-004, SRC-005, SRC-014, SRC-017, SRC-021
- **내용:** active group의 모든 frame은 `display:flex`인 채 stack transform으로 viewport 밖으로 이동하고 frame 단위 `aria-hidden`·`inert`가 없다. 따라서 inactive frame의 텍스트가 접근성 트리에 중복 노출되거나 그 안의 link/control이 tab order에 남을 가능성이 있다. 현재 HTML 속성 부재는 확인했지만 screen reader별 실제 노출은 실행 검증이 필요하다.
- **신뢰도:** DOM 사실은 높음, 실제 보조기술 영향은 중간
- **반례·제약:** SVG/Marp가 생성하는 구체적인 접근성 트리와 authored interactive element 유무에 따라 체감 영향이 달라진다. 단순히 whole slide를 live region으로 만들면 매 이동마다 과도한 내용을 다시 읽는 역효과가 생길 수 있다.
- **결정 영향:** current frame만 exposed/focusable하게 `aria-hidden`·`inert` 또는 동등한 정책을 갱신하고, outgoing frame 안에 focus가 있었다면 예측 가능한 current control/stage로 옮긴다. 위치 announcement는 whole slide 복제가 아니라 짧은 별도 status로 제공한다.

### F-015 — 제품 소유자는 1.1.0의 safe-default·상시 상태형 navigation profile을 확정했다

- **판정:** 제품 결정.
- **근거:** SRC-024.
- **내용:** 1.1.0에서는 common Next/Previous와 stage click을 reading order로 통일하는 safe-default dual-path를 기본으로 사용한다. 하단의 route-aware 이전/다음과 계층 counter는 항상 보이게 하되 one-time coach mark, floating 안내, tutorial-seen persistence는 추가하지 않는다. 사용성 gate는 외부 5인 모집 대신 설명을 가린 owner-blind hallway walkthrough와 deterministic transition/browser matrix로 구성하고, 인간 이해도 근거의 신뢰도는 `medium`으로 유지한다. standalone export의 정식 계약은 desktop browser까지이며 mobile swipe·wheel gesture는 보장하지 않는다.
- **신뢰도:** 제품 결정은 높음; 신규 사용자 이해도 예측은 중간.
- **반례·제약:** owner hallway는 독립 참가자 표본을 대체하지 않는다. 상시 상태만으로 첫 multi-frame continuation을 충분히 발견하지 못한다는 후속 evidence가 나오면 coach mark 재검토에는 새 결정과 보고서 revision이 필요하다.
- **결정 영향:** Q-005, Q-008, Q-010, Q-013과 REC-005의 1.1.0 선택 상태를 해소한다. REC-005 원문은 연구 대안으로 보존하지만 이번 릴리스에서는 **미채택**이며, 그 롤백 문구의 persistent subtle route label만 REC-004/F-015의 상시 상태로 채택한다. 새 설정, render option, parent↔iframe tutorial message를 만들지 않는다.

### F-016 — owner hallway의 계층 이해는 실제 구분 동작과 명시적 sign-off로 확인됐다

- **판정:** 구현 후 owner acceptance decision.
- **근거:** SRC-025.
- **내용:** 설명을 가린 fresh `[1,3,2]` deck에서 owner는 `→`와 `↓`로 reading order를 끝까지 완주하고, 별도 section control로 `2-1 → 3-1`에 이동했다. 관찰 counter는 각각 `Section 3/3 · Slide 2/2`와 `Section 3/3 · Slide 1/2`였다. Owner는 “섹션이랑 슬라이드 구분해서 동작이 다 되니까 릴리즈 단계로 넘어가도 된다”고 명시 확인했다.
- **신뢰도:** owner acceptance는 높음; 신규 사용자 일반화는 기존 결정대로 중간.
- **반례·제약:** 이는 독립 참가자 표본이나 용어 정의 시험이 아니다. 다만 1.1.0 gate의 목적은 section/slide를 구분해 두 navigation path를 실제 수행할 수 있는지 확인하는 것이며, 별도 암기식 정의 답변을 release blocker로 삼지 않는다.
- **결정 영향:** REC-009의 “차이 설명”은 1.1.0에서 실제 계층 구분 동작과 owner의 명시적 구분 확인으로 충족한다. 자동 matrix와 confidence `medium` 조건은 유지한다.

### F-017 — 1.1.3의 fullscreen 버튼 진입은 포커스를 버튼에 남겨 첫 방향키 입력을 차단한다

- **판정:** 배포 코드 사실 및 owner 재현.
- **근거:** SRC-026, SRC-027.
- **내용:** 공개 1.1.3에서 `#btn-fs`를 pointer 또는 native button activation으로 누르면 `requestFullscreen()` 뒤에도 그 버튼이 `document.activeElement`로 남고 visible text만 `Exit`로 바뀐다. document key handler는 모든 `button`을 interactive target으로 판정해 즉시 반환하므로, 사용자가 stage를 한 번 더 클릭하기 전에는 `ArrowRight`와 `ArrowDown`이 navigation을 실행하지 않는다. 기존 acceptance는 body focus에서 `F` 단축키로 진입하는 경로만 검사해 이 버튼 진입 회귀를 놓쳤다.
- **신뢰도:** 높음.
- **반례·제약:** focused native control의 Space/Enter를 control 자체에 맡기는 F-013의 ownership 규칙은 올바르다. 따라서 interactive-target guard를 완화하는 것은 해결책이 아니다.
- **결정 영향:** fullscreen 진입이 실제로 성공한 `fullscreenchange` 시점에 presentation focus sink인 stage로 포커스를 옮기고, 실패 시에는 버튼 포커스를 유지한다. 종료 시에는 별도 강제 이동을 하지 않는다.

### F-018 — 화면 클릭 뒤 나타나는 주황색 테두리는 slide/theme가 아니라 stage의 기본 focus outline이다

- **판정:** DOM/CSS 사실 및 screenshot pixel 관찰.
- **근거:** SRC-026, SRC-027.
- **내용:** owner screenshot의 `#E59700` 계열 1px 선은 2560×1080 viewport 전체가 아니라 하단 control row 56px를 제외한 2560×1024 stage 경계만 둘러싼다. `.achmage-stage`는 `tabindex="-1"`로 programmatic/click focus를 받을 수 있지만 자체 focus style이 없어 Chromium/host의 기본 outline이 노출된다. 반면 실제 interactive control인 하단 button과 vertical dot에는 별도의 흰색 `:focus-visible`이 이미 있다.
- **신뢰도:** 높음.
- **반례·제약:** stage는 sequential tab stop이나 action control이 아니라 outgoing-frame focus 복구용 sink다. 실제 button/dot의 visible focus indicator까지 제거하면 접근성 회귀다.
- **결정 영향:** stage에만 outline을 표시하지 않고, button/dot focus ring은 보존한다. screenshot과 computed style을 함께 acceptance로 고정한다.

### F-019 — owner는 1.1.4에서 deck Home과 명시적 fullscreen toggle을 상시 primary utility로 결정했다

- **판정:** 제품 결정 및 구현 가능성 사실.
- **근거:** SRC-026, SRC-027.
- **내용:** 1.1.3 하단 바에는 keyboard `Home` 계약은 있지만 동일한 visible endpoint control이 없어 긴 deck에서 pointer 사용자에게 반복 Previous를 강요한다. 기존 `firstInDeck()`은 이미 어느 좌표에서도 `(0,0)`으로 이동하므로 새 state나 parser 변경 없이 native Home button을 연결할 수 있다. Owner는 Home을 Previous 앞에 두고 fullscreen action도 `Exit`/`Full` 대신 현재 action을 설명하는 `Fullscreen on`/`Fullscreen off`로 표시하며 두 utility를 고정 ASU teal로 강조하기로 결정했다.
- **신뢰도:** 제품 결정과 코드 가능성은 높음.
- **반례·제약:** 동적 slide-theme accent를 읽으면 theme별 contrast와 coupling이 늘어나므로 patch 범위에서는 사용하지 않는다. Title Case 문구는 Scorecard sentence-case finding을 다시 만들 수 있어 sentence case를 사용한다.
- **결정 영향:** Home은 deck 시작에서 disabled이며 activation 뒤 stage로 포커스를 넘겨 바로 sequential navigation을 이어 간다. wide label은 `Fullscreen on/off`, narrow label은 `FS on/off`, ARIA는 `Enter/Exit fullscreen`과 `aria-pressed`를 유지한다.

## Recommended interaction model

### 1. operation을 먼저 분리한다

다음 transition algebra를 UI와 test의 정본 후보로 삼는다. `G`는 group 수, `F(g)`는 group별 frame 수다.

| operation | 전이 | 끝점 정책 |
|---|---|---|
| `nextInReadingOrder` | `f < F(g)-1`이면 `(g,f+1)`, 아니면 `(g+1,0)` | deck 끝에서 disabled/no-op |
| `previousInReadingOrder` | `f > 0`이면 `(g,f-1)`, 아니면 `(g-1,F(g-1)-1)` | deck 처음에서 disabled/no-op |
| `nextSection` | `(g+1,0)` | 마지막 group에서 disabled/no-op |
| `previousSection` | `(g-1,0)` | 첫 group에서 disabled/no-op |
| `firstInDeck` | `(0,0)` | idempotent |
| `lastInDeck` | `(G-1,F(G-1)-1)` | idempotent |
| `showFrame(f)` | 현재 group의 지정 frame | valid range clamp |

이 정의는 current `nextFrame()`의 전진 동작을 보존하면서 대칭적인 reverse와 정확한 deck endpoints를 추가한다. `showGroup()` 자체를 모든 의미에 재사용해 frame 0 reset을 암묵적으로 만들지 않는다.

### 2. input mapping은 경로의 의미를 드러낸다

먼저 두 prototype에 공통인 mapping을 고정한다. 이 표의 global shortcut은 `e.defaultPrevented === false`이고 focus가 authored link/button/input/select/textarea/contenteditable 등 interactive target 안에 없을 때만 적용한다. 예외로 명시한 `Shift+Space` 외에는 exact unmodified key만 navigation으로 처리하고, `Ctrl/Cmd/Alt` 조합과 focused native control의 Enter/Space는 browser·host·control 본래 동작에 맡긴다.

| input | 권고 action | 이유 |
|---|---|---|
| visible primary `다음` | `nextInReadingOrder` | 이것만 반복하면 누락 없이 완주 |
| visible primary `이전` | `previousInReadingOrder` | Next의 정확한 역함수 |
| stage/body focus의 `Space`, `N`, `PageDown` | `nextInReadingOrder` | current Space 보존, PageDown의 hidden section skip 제거, reveal.js semantic-key 선례 |
| `Shift+Space`, `P`, `PageUp` | `previousInReadingOrder` | 명시적인 역방향 대칭과 reveal.js 선례 |
| stage 오른쪽/왼쪽 click | `nextInReadingOrder`, `previousInReadingOrder` 또는 hidden zone 제거 | generic slide click으로 조용히 frame을 skip하지 않게 함 |
| visible native `다음/이전 섹션` | `nextSection`, `previousSection` | labeled pointer path와 Tab+Enter/Space keyboard path를 함께 제공 |
| `Home`, `End` | `firstInDeck`, `lastInDeck` | glyph/명칭과 실제 endpoint 일치 |
| unmodified `F` | fullscreen | `Ctrl/Cmd+F` 찾기와 충돌하지 않음 |

그 위에서 arrow와 direct section shortcut만 두 variant로 비교한다.

| input | spatial dual-path | safe-default dual-path |
|---|---|---|
| `ArrowRight` / `ArrowDown` | Right=`nextSection`; Down=vertical local | 둘 다 `nextInReadingOrder` |
| `ArrowLeft` / `ArrowUp` | Left=`previousSection`; Up=vertical local | 둘 다 `previousInReadingOrder` |
| direct section shortcut | 기존 Left/Right가 담당 | labeled section button 외에 충돌 검증을 거친 별도 shortcut을 제공; 구체 key/chord는 prototype에서 결정 |
| 장점 | 기존 2D spatial model과 muscle memory 보존 | 사용자가 어떤 흔한 advance key를 눌러도 content skip 없음 |
| 주 위험 | Right 사용자의 silent skip이 남음 | 기존 arrow 의미 회귀와 section shortcut 학습 |

spatial dual-path의 Up/Down 경계도 **Boundary-stop**(section 안에서만)과 **Boundary-wrap**(Down은 다음 section top, Up은 이전 section last)을 비교한다. safe-default가 사용자의 핵심 실패를 가장 직접 막는 선도 후보지만, 직접 test 전에는 기존 2D 사용자 비용을 무시해 확정하지 않는다. 어떤 variant든 invisible stage edge click을 section jump로 유지하지 않는다.

### 3. bottom bar는 route-aware hierarchy를 보여 준다

권고 정보 위계는 다음과 같다.

1. **Primary:** `이전` / `다음` reading-order controls
2. **Status:** `섹션 2/7 · 슬라이드 1/3` 또는 검증된 대체 문구
3. **Secondary:** `이전 섹션` / `다음 섹션`
4. **Tertiary:** first/last/fullscreen/help; narrow pane에서는 compact icon 또는 overflow group

Primary Next에는 실제 다음 route를 보조 신호로 표시할 수 있다.

- 현재 section에 frame이 남음: `다음 ↓`, 보조 상태 `아래 2장`
- section 마지막 frame이며 다음 section이 있음: `다음 →`, 보조 상태 `다음 섹션`
- deck 마지막: disabled + `끝`

Previous도 같은 방식으로 `↑` 또는 `←`를 표시한다. 색 반전은 이 text/shape 변화에 추가하는 강조일 뿐 단독 의미가 아니다.

좁은 pane에서 visible text를 모두 유지할 수 없다면 glyph-only로 단순 축소하기 전에 다음을 비교한다.

- 56px row 안에서 primary label과 계층 counter는 유지하고 secondary/tertiary만 icon으로 축약
- first/last를 `Home/End`와 `?` help에 남기고 visible row에서 우선순위를 낮춤
- full width/fullscreen에서 label을 확장하고 side pane에서 responsive 축약

### 4. first-encounter cue는 맥락적이고 비강제적이어야 한다

첫 multi-frame group의 첫 frame에서만 primary Next에 붙여 다음을 보여 준다.

> ↓ 이 섹션에 슬라이드가 2장 더 있습니다
> `다음` 또는 `Space`로 계속

조건은 다음과 같다.

- 실제 `frameCountFor(gIdx) > 1 && fIdx === 0`일 때만 표시
- 사용자가 Next/Down/Space/dot로 vertical frame에 한 번 도달하면 해제
- timer만으로 사라지지 않고 dismiss 가능
- 같은 iframe session에서는 반복하지 않음; audit/hot reload persistence는 parent view 또는 명시적 render option으로 보존
- `prefers-reduced-motion: reduce`에서는 cue bounce뿐 아니라 frame-stack transform transition과 horizontal group-enter animation을 포함한 모든 비필수 navigation motion을 제거
- motion을 쓰더라도 짧고 제한된 횟수이며 의미는 text/shape로 남음
- `?` help에서 언제든 keyboard map과 2D 구조를 다시 확인 가능

여기서 reduced-motion 처리는 WCAG 2.2 SC 2.3.3 Level AAA 및 일반적인 motion-sensitivity best practice를 계획 기준으로 채택하는 것이며, 이 보고서가 제품의 전체 WCAG 등급 준수를 판정한다는 뜻은 아니다.

`?` help를 modal dialog로 구현한다면 열 때 dialog 안의 의미 있는 첫 element로 focus를 옮기고, `Escape`와 명시적 닫기 control을 제공하며, 닫을 때 trigger로 focus를 돌리고, 열린 동안 background slide navigation을 막는다. non-modal popover를 택해도 trigger의 expanded state와 keyboard dismissal/return-focus를 검증한다.

### 5. dots와 overview는 secondary로 둔다

- dots는 current frame locator 또는 직접 jump로 유지할 수 있지만, hierarchy 설명과 primary continuation control을 대신하지 않는다.
- dot별 tab stop이 과도해지지 않도록 roving focus, grouped control, 또는 비interactive status를 검토한다.
- optional overview는 `2×N` 구조가 아니라 실제 variable frame count를 보여 주고, 필요할 때만 열리는 보조 route다.
- wheel/trackpad는 발견 가능성 문제의 해법이 아니라 추가 input convenience이므로 별도 opt-in 검증 없이는 넣지 않는다.

## Impact analysis

### 제품과 UX

초보자는 visible Next만으로 모든 frame을 누락 없이 볼 수 있고, 숙련자는 section skip을 잃지 않는다. 계층 counter와 route-aware cue는 현재 위치, 아래 잔여량, 다음 action을 동시에 설명한다. permanent chrome은 56px row 안에 제한해 slide 방해를 최소화한다.

잘못된 위계로 primary와 secondary button을 같은 무게로 나열하면 오히려 복잡해질 수 있다. 따라서 pixel design보다 operation priority와 responsive 축약 규칙을 먼저 prototype한다.

### 아키텍처와 데이터

`SlideMapEntry`, Pretext, parser에는 새 field가 필요 없다. UI state는 `gIdx`, `fIdx`, `frameCountFor(gIdx)`, `totalGroups`, `groupData[gIdx].title`의 순수 파생값이어야 한다. transition 함수를 inline IIFE에서 분리해 test 가능한 reducer/module로 옮길지는 계획에서 결정하되 output HTML의 self-contained 조건을 유지한다.

### 성능과 자원 사용

counter와 route arithmetic은 `groupData[gIdx].frames`를 정본으로 쓰면 O(1)로 만들 수 있다. 그러나 current `frameCountFor()`는 `querySelectorAll('.achmage-frame')`을 수행하고 dots도 매 frame마다 재생성하므로 실제 update는 O(F)다. 긴 stack에서 dot DOM을 재사용할지 측정하고, tutorial animation과 overview를 넣을 경우 layout/paint도 확인한다. parser와 audit pass 수에는 영향을 주지 않아야 한다.

### 보안과 개인정보

navigation은 local DOM state만 사용하며 네트워크나 telemetry가 필요 없다. `README.md:47`의 no analytics 약속을 유지한다. 사용성 검증은 동의받은 local session과 익명 aggregate note로 수행하고 개인 vault 내용을 보고서에 복사하지 않는다.

### 호환성과 마이그레이션

PageDown/PageUp, arrow, bottom Prev/Next, Home/End 의미 변경은 선택 variant에 따라 기존 사용자에게 behavioral change다. release note와 `?` help가 필요하다. optional legacy/spatial setting을 추가할지는 사용성 test 결과로 결정하며, 설정을 추가한다면 default/migration을 명시한다.

live preview와 export가 같은 shell을 공유하므로 기본은 양쪽 동일 grammar를 권고한다. preview-only tutorial을 원하면 render mode flag가 필요하지만 exported viewer가 더 novice일 수 있다는 반대 근거가 있다.

### 테스트와 관측 가능성

다음 세 층을 분리한다.

1. **Pure transition:** topology `[1]`, `[1,1]`, `[3]`, `[1,3,2]`, `[3,1]`의 모든 `(g,f)`에서 각 operation 결과를 table test한다.
2. **Browser DOM/a11y:** key, button, stage click, dot, modifier, disabled state, counter, iframe/control accessible name, active-frame exposure, focus-visible, live feedback, reduced motion을 real Chromium에서 검사한다.
3. **Human comprehension:** current, 사용자 안 2 강화형, spatial dual-path, safe-default dual-path를 설명 없이 비교한다. 사용자 안 1의 핵심인 common-key 선형화는 safe-default형에 포함하되 pointer-only section jump 결함은 제거한다.

관측 지표 후보는 다음과 같다. 이는 아직 달성값이 아니라 다음 계획의 gate 후보다.

- 첫 multi-frame group에서 10초 안에 다음 frame을 발견한 비율
- primary Next 반복 시 skipped/duplicated frame 수가 0인지
- section skip task를 한 번의 명시적 action으로 수행하는지
- `다음 슬라이드`와 `다음 섹션` 차이를 사용 후 설명할 수 있는지
- help 요청 수, 첫 잘못된 section skip 수, task completion time
- 기존 사용자의 section jump action 수가 늘지 않는지

5명 formative test에서는 4/5 이상이 instruction 없이 vertical continuation을 찾는 것을 prototype 통과 후보로 삼되, 이를 모집단 성공률로 일반화하지 않는다.

### 빌드, 배포, 문서

shell source 변경은 build 후 committed `main.js`를 재생성해야 한다. README Usage와 demo 첫 부분에 compact key map을 추가하고, exported HTML에는 `?` help를 포함한다. 실행 시 typecheck, build, navigation harness, overflow matrix의 대표 font/topology subset, governance check를 기록한다.

## Verification design for the next plan

### State reachability

- `[1,3,2]`에서 Next 반복 결과가 정확히 `0-0,1-0,1-1,1-2,2-0,2-1`이고 각 좌표를 한 번만 방문한다.
- Previous 반복은 위 순서의 정확한 역순이다.
- section Next/Previous는 항상 대상 frame 0으로 이동하고 intermediate frame을 의도적으로 skip한다.
- first/last는 어느 현재 frame에서 호출해도 정확히 deck endpoint다.
- key repeat와 final boundary가 accidental double advance를 만들지 않는다.
- 각 native navigation button에 focus한 뒤 `Space`/`Enter`를 누르면 그 focused button의 action만 정확히 한 번 실행되고 global `nextInReadingOrder`가 추가로 실행되지 않는다.
- authored link/button/input/select/textarea/contenteditable에 focus했을 때 Space·Arrow·Page·Home/End를 global navigation이 가로채지 않고, 이미 `defaultPrevented`인 synthetic event도 state를 바꾸지 않는다.
- `Ctrl/Cmd/Alt/Shift` 조합은 명시한 `Shift+Space` 외에는 navigation/fullscreen을 실행하지 않는다. 특히 `Ctrl/Cmd+F`가 fullscreen을 토글하지 않는지 확인한다.

### UI truthfulness

- counter, active dot, route cue, button label/disabled, `achmageGroupIndex/achmageFrameIndex`, stack transform이 항상 같은 좌표를 나타낸다.
- frame 잔여 시 `아래 있음`, section boundary 시 `다음 섹션`, deck end 시 `끝`이 color 없이 구분된다.
- retained pointer control은 keyboard equivalent와 descriptive accessible name을 가진다. 보이지 않는 stage edge zone은 제거하거나 실제 semantic control로 만들며 이름 없는 click target으로 남기지 않는다.
- visible icon을 작게 유지하더라도 primary target은 최소 24×24 CSS px 또는 기준의 허용 조건을 실제 computed geometry로 확인한다.
- meaningful non-text control/state contrast는 light/dark·고대비 후보에서 3:1 이상, 새 counter·label·coach text 같은 일반 크기 text는 배경 대비 4.5:1 이상을 별도로 측정한다.
- current frame만 접근성 트리에 노출되고 tabbable해야 한다. inactive frame은 `aria-hidden`·`inert` 또는 검증된 동등 정책으로 제외하며, frame 전환 때 outgoing content의 focus가 보이지 않는 곳에 남지 않는다.
- position announcement는 available한 section title과 `2/7 · 1/3` 같은 짧은 별도 status만 전달하고 inactive/active slide 전체 내용을 중복해서 live announce하지 않는다.
- iframe은 preview 목적을 설명하는 accessible `title`을 갖고, visually hidden/disabled control의 programmatic state도 `opacity`/pointer state와 동시에 갱신된다.
- `?` help가 dialog/popover라면 open→focus entry→background navigation 차단→Escape/닫기→trigger focus 복귀의 전체 lifecycle을 keyboard-only로 검증한다.
- `prefers-reduced-motion: reduce`에서 coach-mark, vertical transform, horizontal enter를 포함한 비필수 motion의 computed animation/transition이 제거된다.

### Parser and lifecycle non-regression

- 동일 Markdown/settings를 3회 render했을 때 group/frame topology와 shell state가 동일하다.
- 16→40→16pt 왕복 후 최종 topology가 첫 16pt와 동일하고 restored index는 valid range다.
- `headingDivider:[2]`, `[1,2]`, `[2,3,4]`, `autoContinuedFrames` on/off, Tier 2 on/off, title/manual break를 포함한다.
- audit pass 0과 corrected pass에서 HUD가 반복 animation이나 stale state를 남기지 않는다.
- narrow Obsidian pane, 1920×1080 fullscreen, exported HTML에서 56px control row가 overflow하거나 slide를 가리지 않는다.
- overflow probe의 `.achmage-logical-group`, `.achmage-frame-stack`, `.achmage-frame section` selector와 ≤2px 기준이 유지된다.

## Recommendations

### REC-001 — 2D parser model을 보존하고 presentation shell만 변경한다

- **근거 Finding:** F-001, F-004, F-010, F-012
- **권고:** Pretext, `splitOverflowingSlides`, `SlideMapEntry`, frame DOM hierarchy, overflow probe selector를 건드리지 않고 `buildPresentationHTML()`의 control/state layer에서 UX를 개선한다.
- **채택 조건:** parser topology·overflow acceptance가 baseline과 동일하고 UI가 existing group/frame data만 읽어야 한다.
- **기각/롤백 조건:** 필요한 UX state를 existing topology에서 계산할 수 없다는 재현 가능한 증거가 생기면 별도 연구로 data model 확장을 검토한다.

### REC-002 — Dual-path navigation을 기본 interaction architecture로 채택한다

- **근거 Finding:** F-002, F-005, F-007
- **권고:** visible sequential Prev/Next를 primary로, labeled section Prev/Next를 secondary로 제공한다. arrow를 2D로 보존하는 spatial형과 common Next/Previous까지 reading order로 보내는 safe-default형을 비교하되 safe-default를 선도 후보로 둔다. 어느 쪽이든 section jump는 pointer와 keyboard-accessible path 양쪽에서 유지하고, 보이지 않는 stage edge는 reading-order click으로 바꾸거나 제거해 silent skip surface로 남기지 않는다.
- **채택 조건:** novice가 어떤 primary/common Next path에서도 frame을 건너뛰지 않고, expert section-skip task도 명시적인 pointer와 keyboard path로 완료하며, control hierarchy가 narrow pane에서 이해 가능해야 한다.
- **기각/롤백 조건:** prototype에서 dual controls가 current/사용자 안 2 강화형보다 유의미하게 더 많은 오조작을 만들면 단일 route-aware Next + help로 축소하되 section shortcut은 help/configurable path에 보존한다.

### REC-003 — 대칭적인 reading-order operation과 정확한 endpoint를 정의한다

- **근거 Finding:** F-002, F-011, F-013
- **권고:** `nextInReadingOrder`, `previousInReadingOrder`, `nextSection`, `previousSection`, `firstInDeck`, `lastInDeck`을 명시하고 transition table로 고정한다. stage/body focus의 Space/N/PageDown과 Shift+Space/P/PageUp을 sequential pair 후보로 검증하되 interactive target과 host modifier shortcut에는 적용하지 않는다.
- **채택 조건:** topology matrix에서 forward와 reverse가 정확한 역순이고 first/last가 어느 상태에서도 같은 endpoint여야 한다.
- **기각/롤백 조건:** 기존 key behavior 회귀가 사용성 이득보다 크면 key binding만 legacy로 유지하되 visible semantic controls의 대칭성은 유지한다.

### REC-004 — 계층 위치와 실제 다음 route를 하단 bar에 표시한다

- **근거 Finding:** F-003, F-006, F-008
- **권고:** counter를 group+frame 형식으로 바꾸고 primary Next/Previous 및 endpoint control의 arrow·label·disabled state가 다음 실제 route와 availability를 나타내게 한다. accessible position에는 가능하면 `groupData[g].title`과 계층 번호를 함께 쓰되 visible bar 폭은 늘리지 않는다. dots와 색은 secondary status로만 쓴다.
- **채택 조건:** frame 이동마다 visible/accessible status가 갱신되고 color 없이 `아래`, `다음 섹션`, `끝`을 구분할 수 있어야 한다.
- **기각/롤백 조건:** counter 문구가 narrow layout을 깨면 explicit labels는 accessible text/help에 유지하고 visible compact format을 사용자 test로 선택한다.

### REC-005 — 최초 vertical encounter에 한정한 coach mark와 상시 help를 제공한다

- **근거 Finding:** F-008, F-010
- **권고:** 첫 multi-frame group에서 action-dismissible cue를 보여 주고 한 번 vertical navigation 후 숨긴다. `?` help에는 full key map과 two-path 설명을 유지하고 dialog/popover focus lifecycle을 명시한다.
- **채택 조건:** audit/hot reload 중 cue가 반복되지 않고 reduced-motion 설정에서 cue와 기존 navigation motion이 모두 정적으로 이해되며 timer 없이도 읽을 수 있어야 한다. help는 keyboard로 열고 닫은 뒤 trigger focus가 복구되어야 한다.
- **기각/롤백 조건:** formative test에서 cue가 content를 방해하거나 반복 annoyance가 높으면 animation을 제거하고 persistent subtle route label만 유지한다.

### REC-006 — navigation controls와 frame 노출을 semantic·keyboard·pointer 접근성 기준으로 재구성한다

- **근거 Finding:** F-006, F-009, F-013, F-014
- **권고:** clickable div 대신 native button 우선, descriptive accessible names, focus-visible, route availability/disabled, 충분한 hit area·spacing, non-text 3:1과 normal-text 4.5:1 contrast, color 외 cue를 적용한다. iframe에 accessible title을 주고 global key handler에는 default-prevented·interactive-target·exact-modifier guard를 두며 current frame만 exposed/focusable하게 만든다.
- **채택 조건:** keyboard-only로 모든 retained pointer 기능을 수행하고, focused native button의 Space/Enter가 정확한 action만 한 번 실행하며, 실제 computed target/contrast·iframe/control name·screen reader status·inactive-frame tab/a11y exclusion을 검증해야 한다.
- **기각/롤백 조건:** 없음. 시각 크기를 줄일 수는 있어도 semantic operation과 equivalent access는 제거하지 않는다.

### REC-007 — 구현 전에 네 prototype과 transition/a11y harness를 검증한다

- **근거 Finding:** F-005, F-007, F-011, F-013, F-014
- **권고:** current, 사용자 안 2 강화형, spatial dual-path, safe-default dual-path를 동일 task로 비교하고, 선택안은 pure state matrix와 real-browser DOM/a11y regression을 먼저 만든 뒤 shell을 수정한다. harness에는 focused-control Space, modifier/defaultPrevented guard, inactive-frame accessibility tree와 focus 복구를 포함한다.
- **채택 조건:** 신규 사용자 vertical 발견, no-skip reading, expert section jump, narrow layout에서 사전 정의한 gate를 통과해야 한다.
- **기각/롤백 조건:** 직접 사용자 모집이 불가능하면 최소한 owner-blind hallway test와 deterministic automated matrix를 통과시키고 confidence를 중간으로 유지한다.

### REC-008 — preview와 export는 기본적으로 같은 grammar를 사용한다

- **근거 Finding:** F-003, F-010
- **권고:** 같은 HTML shell을 공유하는 장점을 유지하고 exported viewer에도 sequential primary path, section path, counter, help를 제공한다. tutorial persistence mechanics만 host별로 달리할 수 있다. 계획에서 standalone export의 지원 플랫폼을 desktop browser로 한정할지 mobile/touch까지 포함할지 명시한다.
- **채택 조건:** exported file을 승인된 독립 브라우저·device 범위에서 열어 모든 navigation·a11y state를 검증해야 한다. mobile 지원이면 touch target/gesture/device matrix를 추가하고, 미지원이면 desktop-only 제약을 문서화한다.
- **기각/롤백 조건:** export 소비자 시나리오에서 controls가 불필요하다는 근거가 생기면 explicit render mode를 도입하되 key grammar 의미는 같게 유지한다.

### REC-009 — 1.1.0에는 owner-selected safe-default·상시 상태형 profile을 적용한다

- **근거 Finding:** F-002, F-003, F-005, F-007, F-011, F-015.
- **권고:** `Right`/`Down`/`PageDown`/`Space`/`N`과 stage 오른쪽 click은 `nextInReadingOrder`, `Left`/`Up`/`PageUp`/`Shift+Space`/`P`와 stage 왼쪽 click은 `previousInReadingOrder`로 통일한다. section jump는 별도 native `이전/다음 섹션` button의 pointer 및 Tab+Enter/Space 경로로 제공하며 새 global section shortcut은 만들지 않는다. 하단에는 실제 route arrow와 `Section 2/7 · Slide 1/3` 계층 상태를 상시 표시하고 coach mark는 넣지 않는다.
- **채택 조건:** owner-blind hallway에서 continuation 발견, primary Next 완주, 명시적 section jump, section/slide 차이 설명을 모두 수행하고, 자동 matrix가 no-skip·exact reverse·input ownership·a11y·desktop export를 통과해야 한다. 인간 이해도 confidence는 `medium`으로 기록한다.
- **기각/롤백 조건:** 상시 상태가 owner hallway에서 continuation 발견을 실패하면 조용히 coach mark를 되살리지 않고 R-002를 revision하여 원인과 새 UI 대안을 다시 결정한다. mobile gesture 요구는 별도 연구로 분리한다.

### REC-010 — owner hallway는 정의 암기보다 계층별 실제 조작을 판정한다

- **근거 Finding:** F-016.
- **권고:** continuation 발견·primary 완주·section jump를 실제 수행하고 owner가 section/slide 구분 동작 정상과 release 진행을 명시 확인하면 1.1.0 hallway gate를 통과한다. 독립 사용자 이해도 주장은 하지 않고 confidence를 `medium`으로 유지한다.
- **채택 조건:** 자동 matrix와 관찰 counter가 owner 보고와 일치해야 한다.
- **기각/롤백 조건:** owner가 두 path를 혼동하거나 counter와 보고가 불일치하면 AC-206을 통과시키지 않는다.

### REC-011 — fullscreen mode 전환 뒤 presentation focus를 명시적으로 소유한다

- **근거 Finding:** F-013, F-014, F-017, F-018.
- **권고:** fullscreen 진입이 성공한 경우에만 stage를 `preventScroll`로 focus하고 stage의 비대화형 focus outline만 제거한다. request 실패와 fullscreen 종료의 기존 focus를 보존하며 interactive-target guard, focused control Space/Enter, button/dot focus-visible을 변경하지 않는다.
- **채택 조건:** button click과 Enter 진입 모두에서 추가 click 없이 첫 Right/Down이 정확히 한 frame 이동하고, stage perimeter가 보이지 않으며 실제 control focus ring은 유지되어야 한다.
- **기각/롤백 조건:** stage focus가 authored control ownership, Escape 종료, export 또는 accessibility tree를 회귀시키면 focus tranche를 rollback하고 별도 focus proxy 설계를 연구한다.

### REC-012 — 기존 endpoint operation에 visible Home과 action-oriented fullscreen label을 연결한다

- **근거 Finding:** F-003, F-007, F-009, F-019.
- **권고:** Home native button을 Previous 앞에 추가해 `firstInDeck()`에만 연결하고 시작점에서 disabled로 표시한다. Home activation 뒤 stage로 focus를 넘긴다. Fullscreen은 sentence-case on/off action label과 기존 ARIA state를 사용하며 두 utility는 fixed shell teal `#00B5AD`와 near-black ink `#061A19`로 강조한다.
- **채택 조건:** 모든 topology와 input modality에서 Home이 `(0,0)`에 한 번만 도달하고, 320/480/800/1920px에서 bar overflow가 없으며 text/control contrast와 live/export parity가 통과해야 한다.
- **기각/롤백 조건:** 좁은 폭이나 Scorecard가 악화되면 동적 theme coupling을 추가하지 않고 compact label/layout을 먼저 축소한다.
