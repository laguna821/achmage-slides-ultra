# R-007 — 1.1.1 draft 생성 실패와 1.1.2 forward-fix

## Executive summary

- **결론:** `1.1.1`의 제품·navigation·build·quality·attestation은 정상이다. 실제 tag run `30836179184`는 build job 전체와 release job의 asset 검증, annotated-tag 재검증, 세 asset attestation 생성·검증, 한·영 notes 확인을 통과한 뒤 `gh release create --verify-tag`에서만 `fatal: not a git repository`로 실패했다.
- **정확한 원인:** checkout 없는 asset-only release job에서 `gh release create`가 대상 repository를 자동 판별하려 했지만 current directory에 `.git`이 없었다. GitHub CLI `2.96.0` source에서 `--verify-tag`는 지정된 remote repository의 tag 존재를 API로 검사하고, 명시적 `--repo`가 있으면 local `gitTagInfo` 경로를 건너뛴다. 따라서 원인은 `--verify-tag`가 local tag object를 요구해서가 아니라 **`--repo`가 빠져 repository context를 local Git에서 찾은 것**이다.
- **최소 수정:** 기존 command에 `--repo "$GITHUB_REPOSITORY"` 한 줄만 추가한다. Release job checkout·`git init`·tag fetch는 추가하지 않고, `--verify-tag`, annotated tag object/name/direct target/SHA, exact-main, attestation, exact three assets, draft-only, post-write ref/hash guard는 모두 유지한다.
- **제품 결정:** 사용자가 확인한 순차 navigation과 `2-1 → 3-1` section jump를 포함한 제품 코드는 되돌리지 않는다. `97a1e0b…c6e` 대비 `src/**`, `styles.css`, `main.js` diff는 0이다.
- **릴리스 결정:** 이미 push된 `1.1.1` tag와 생성된 attestation을 삭제·이동·덮어쓰거나 수동으로 asset을 올리지 않는다. Workflow 한 줄, version tuple과 notes만 `1.1.2`로 전진시키고 exact new `main` SHA에 annotated tag를 push한다. Actual tag event가 non-prerelease draft와 세 asset의 server-side hash·attestation을 모두 통과한 뒤 사람 검토 대상으로 넘긴다.
- **남은 불확실성:** `gh release create`에는 write 없는 dry-run이 없다. Static/source/repository-context 재현은 가능하지만 실제 draft write는 `1.1.2` tag event에서 최종 확인해야 한다. 실패하면 publish·retag·asset overwrite 없이 중지한다.

## Research brief

### 배경과 의사결정

P-003/E-003에 따라 exact `main` SHA `97a1e0b8f7bfb37db4a599f93e99a8b70f9c3c6e`에 annotated `1.1.1` tag를 push했다. Run `30836179184`는 이전 `1.1.0` checkout-local tag 문제를 해결해 build와 signing을 통과했으나 draft 생성 직전에 실패했다. 사용자는 좌·우/상·하 reading-order 이동, section/slide 구분과 `2-1 → 3-1` section jump가 모두 정상임을 확인하고 릴리스 진행을 승인했다. 따라서 이번 의사결정은 제품 UX를 바꿀지가 아니라 **검증된 제품과 공급망 guard를 유지하면서 release command에 올바른 repository context를 어떻게 제공할지**다.

### 핵심 질문

1. `1.1.1` run은 어느 단계까지 성공했고 정확히 어디서 실패했는가?
2. 실패는 제품·asset·tag·attestation 결함인가, release job command context 결함인가?
3. `gh release create`가 local Git을 호출한 경로와 `--repo`의 정확한 효과는 무엇인가?
4. `--verify-tag`와 asset-only/no-checkout 설계를 유지하는 최소 수정은 무엇인가?
5. Immutable `1.1.1` tag와 attestation을 보존하면서 어떤 version으로 전진해야 하는가?

### 성공 기준

- 실패 run의 job/step/log, tag object, release 부재와 product diff를 서로 대조한다.
- 실행된 GitHub CLI와 같은 `v2.96.0` source에서 repository override, remote tag verification, local Git branch를 확인한다.
- `.git`이 없는 directory에서 `--repo` 유무에 따른 read-only release command의 repository resolution 차이를 재현한다.
- 제품 revert 없이 `1.1.2`로 전진하는 단일 권고, 기각 대안, 롤백 조건과 검증 가능한 planning handoff를 제공한다.

## Findings

### F-001 — `1.1.1`은 제품/품질 실패가 아니라 draft command context 실패다

- **판정:** 사실 + 관찰
- **근거:** SRC-001, SRC-002
- **내용:** Build job의 모든 실질 step과 release job의 `Create release` 이전 실질 step이 성공했다. Failure environment에는 expected tagged SHA, tag-object SHA와 세 asset hash가 있었고 API 기반 `assert_release_refs`까지 통과했다. 이어지는 `gh release create`가 local Git repository 부재로 종료됐다.
- **신뢰도:** 높음.
- **반례·제약:** 실제 draft가 없어 post-write asset download/hash step은 실행되지 않았다.
- **결정 영향:** 제품, bundle, tag identity, attestation guard를 revert하거나 완화하지 않는다.

### F-002 — checkout 없는 release job과 repository auto-resolution이 충돌했다

- **판정:** 사실
- **근거:** SRC-002, SRC-004
- **내용:** `.github/workflows/release.yml:245-259`의 release job은 checkout 없이 세 asset만 workspace에 내려받는다. `:261-296`은 top-level regular file을 정확히 세 개로 제한하고, 이후 tag 검사는 `gh api`에 explicit repository path를 사용한다. 반면 `:428-433`의 `gh release create`만 repository override 없이 실행된다. `.git`이 없는 directory에서 release subcommand도 `--repo`가 없으면 동일한 Git 오류, `--repo`가 있으면 지정 repository API 응답을 반환했다.
- **신뢰도:** 높음.
- **반례·제약:** CLI 구현이 향후 repository context 처리 방식을 바꿀 수 있다.
- **결정 영향:** Asset-only/no-checkout 경계는 유지하고 write command에 repository를 명시한다.

### F-003 — `--verify-tag`는 remote API guard이며 이번 오류의 원인이 아니다

- **판정:** 사실
- **근거:** SRC-003, SRC-005
- **내용:** GitHub CLI `v2.96.0` source `create.go:148-150`은 `--repo` 값을 `RepoOverride`에 저장한다. `:258-266`은 `--verify-tag`가 `remoteTagExists(httpClient, baseRepo, tag)`를 호출해 remote tag 존재를 검사함을 보여준다. Local `gitTagInfo`는 그 뒤 `:269-294`에서 `RepoOverride == ""`인 경우에만 실행된다. 즉 explicit `--repo`는 remote verification을 유지하면서 불필요한 local Git branch만 건너뛴다.
- **신뢰도:** 높음; 실행 CLI와 같은 immutable source commit `b300f2e…ca0` 기준.
- **반례·제약:** `--repo`와 `--notes-from-tag`는 함께 쓸 수 없지만 현재 workflow는 explicit `--notes-file`을 사용하므로 영향이 없다.
- **결정 영향:** `--verify-tag`를 삭제하지 않고 `--repo "$GITHUB_REPOSITORY"`를 추가한다.

### F-004 — `--repo "$GITHUB_REPOSITORY"` 한 줄이 가장 좁고 fail-closed인 수정이다

- **판정:** 추론 + 권고
- **근거:** SRC-002, SRC-003, SRC-004
- **내용:** Explicit repository는 current CLI가 local tag description/commit-log 경로로 들어가는 것을 막고, 이미 제공되는 title과 notes-file 때문에 출력 의미도 바꾸지 않는다. API 기반 annotated object/name/direct-target/exact-SHA 검사는 write 직전과 뒤에 남고, `--verify-tag`도 remote existence를 다시 확인한다. Checkout, `git init`, tag fetch, 직접 REST 구현은 불필요하다.
- **신뢰도:** 높음; actual write 성공은 tag event에서 확인.
- **반례·제약:** API precheck와 write 사이의 작은 race와 partial draft 가능성은 기존과 같으며 post-write guard가 탐지한다.
- **결정 영향:** Workflow functional diff를 이 한 줄로 제한한다.

### F-005 — `1.1.1`은 고정하고 `1.1.2` normal tag event로 전진해야 한다

- **판정:** 사실 + 권고
- **근거:** SRC-001, SRC-006, R-006/F-003,F-004
- **내용:** `1.1.1` annotated tag는 exact `main`을 가리키고 그 tag-event는 세 asset attestation을 생성했지만 release/draft/assets는 만들지 못했다. 이미 고정된 tag를 이동해 workflow snapshot을 바꿀 수 없으므로, workflow fix와 version tuple/notes를 새 `main`에 병합한 뒤 annotated `1.1.2` tag event를 사용하는 것이 tag→workflow→source→attestation identity를 일치시킨다.
- **신뢰도:** 높음; actual `1.1.2` draft는 post-tag 확인 필요.
- **반례·제약:** 공개 version이 1.0.3에서 1.1.2로 건너뛴 이유를 notes에 설명해야 한다.
- **결정 영향:** Immutable `1.1.0`/`1.1.1`을 보존하고 `1.1.2` forward-fix를 만든다.

### F-006 — forward-fix의 제품 내용은 승인된 candidate와 byte-identical해야 한다

- **판정:** 사실 + 권고
- **근거:** SRC-006, R-006/F-005
- **내용:** Baseline에서 `src/**`, `styles.css`, `main.js` diff가 0이고 사용자는 navigation을 직접 통과시켰다. 이번 정상 범위는 workflow, R/P/E/Register, version tuple, `1.1.2` notes다. Clean build의 `main.js`가 기존 5,268,064 bytes, SHA-256 `87b0f0f6baa5f8036ec94a06f4a40de8f7aa667c5a5aaf562ab904a3908451c2`와 byte-identical이어야 no-revert를 증명한다.
- **신뢰도:** 높음; final clean build로 재확인.
- **반례·제약:** Manifest/package version은 의도적으로 바뀐다.
- **결정 영향:** Product allowlist diff, acceptance:all, clean artifact hash와 exact candidate Scorecard를 다시 gate한다.

## Impact analysis

### 제품과 UX

사용자가 확인한 reading-order navigation, section jump, counter, parser와 overflow는 바꾸지 않는다. 공개 1.0.3 대비 UX 개선은 1.1.2 release notes에 유지하며, 미공개 1.1.1 candidate 대비 추가 제품 동작은 없다.

### 아키텍처와 데이터

Plugin runtime, TypeScript API, settings schema, vault data, dependency graph과 migration에는 변화가 없다. GitHub Actions release command context와 version tuple만 바뀐다.

### 성능과 자원 사용

제품 및 runner runtime 성능 변화는 실질적으로 없다. Checkout/fetch도 추가하지 않는다.

### 보안과 공급망

`--verify-tag`, annotated object/name/direct-target/commit identity, exact-main, same-SHA Governance, three-asset hash, attestation source ref/digest, draft-only와 post-write ref/hash guard를 모두 유지한다. `--repo` 값은 GitHub가 제공하는 `GITHUB_REPOSITORY` context에서 읽는다.

### 호환성과 마이그레이션

Obsidian 최소 버전 `1.7.2`, desktop-only export 정책과 plugin storage는 동일하다. `versions.json`에는 기존 entries를 보존한 채 `1.1.2: 1.7.2`만 append한다.

### 테스트와 관측 가능성

Pinned source audit, no-Git repository-resolution reproduction, workflow functional diff, YAML/bash syntax, version tuple, clean build/hash, acceptance:all, lint, audits, preflight, Governance와 exact candidate Dashboard preview를 실행한다. Post-tag run에서 draft state, 세 server-side asset/hash와 attestation source ref/digest를 직접 확인한다.

### 빌드·배포·문서

`docs/release/1.1.2.md`는 1.0.3 이후 UX/Scorecard 변경과 `1.1.0`·`1.1.1`이 공개되지 않은 이유를 한·영으로 설명한다. Workflow는 exact tag commit에서 notes를 읽고 draft만 생성한다.

## Recommendations

### REC-001 — release create에 explicit repository override를 추가한다

- **근거 Finding:** F-001,F-002,F-003,F-004
- **권고:** `gh release create "$RELEASE_VERSION"`에 `--repo "$GITHUB_REPOSITORY"`를 추가한다.
- **채택 조건:** Workflow functional diff가 한 option으로 제한되고, no-Git workspace, explicit notes-file, `--verify-tag`와 exact asset arguments를 유지한다.
- **기각/롤백 조건:** Checkout/local tag/source execution이 필요하거나 CLI가 explicit repo에서도 local Git을 요구하면 publish를 중지하고 R-007을 갱신한다.

### REC-002 — 기존 release trust guards를 한 줄도 완화하지 않는다

- **근거 Finding:** F-003,F-004
- **권고:** Annotated tag API identity, exact main, same-SHA Governance/quality, asset hashes, attestation source ref/digest, draft-only와 pre/post-write 검증을 그대로 유지한다.
- **채택 조건:** Static contract diff와 actual run에서 모든 guard가 PASS.
- **기각/롤백 조건:** `--verify-tag`, attestation 또는 post-write 검증 제거가 필요하면 tranche를 기각한다.

### REC-003 — `1.1.1`을 변경하지 않고 `1.1.2` tag-event forward-fix를 사용한다

- **근거 Finding:** F-005,F-006
- **권고:** Workflow 한 줄, R/P/E, 1.1.2 tuple/notes만 new main에 병합하고 exact main green 뒤 annotated no-`v` `1.1.2` tag를 push한다.
- **채택 조건:** Product source diff 0, clean `main.js` hash equality, quality/Scorecard/Governance pass, actual draft/three assets/attestation pass.
- **기각/롤백 조건:** `1.1.0`/`1.1.1` ref 또는 asset을 수정해야 하거나 product diff가 생기면 중지한다.
